# Участие в разработке Planveyor

[English](CONTRIBUTING.md) · **Русский**

Делайте изменения ограниченными, удобными для ревью и безопасными для публикации. Зачем нужен артефакт Planveyor, должно быть видно из текущего плана, ревью, issue или пакета, который его требует.

## Перед правкой

Начните с публичного фасада команд:

```zsh
./bin/planveyor planveyor_entry_doctor
./bin/planveyor planveyor_help
```

Прежде чем менять контракт жизненного цикла, прочитайте документ роли, промпт, плейбук и шаблон, которые к нему относятся. В проекте, который пользуется Planveyor, запускайте его собственные тесты и следуйте правилам участия из этого проекта.

## Локальные предпосылки и проверка

Первый выпуск поддерживается на macOS, в одном активированном окружении Python 3.12 с версиями пакетов, закреплёнными в `requirements-dev.lock`, в том числе Copier 9.18.2 и PyYAML. Создайте это окружение сами, один раз выполните в нём `make bootstrap-python`, держите его активированным и сделайте Git, zsh и ripgrep доступными в `PATH`. Planveyor не устанавливает и не чинит зависимости. Если предпосылки нет, команда завершается с ошибкой, в которой она названа. Диапазон Python 3.10–3.12 задаёт только техническую границу загрузчика. Второго поддерживаемого пути он не открывает. Матрицу CI на macOS запускает GitHub Actions: полный набор в 14 частях на Python 3.12 и выборку тестов совместимости `compat310` на Python 3.10, см. [маршруты проверки](docs/tools/verify_suite.ru.md). Первый успешный прогон прошёл 1 ноября 2026 года, но CI пока не стал устойчиво зелёным; это пункт [F5](docs/release_backlog.md#f5) в обязательствах первого выпуска. Результат CI относится к тому коммиту, на котором шёл прогон; сама по себе настроенная матрица результата не даёт. Поддержка других версий Python и нативная проверка на Windows и Linux остаются отложенными задачами на время после выпуска.

Выбирайте самый короткий маршрут, который доказывает изменённый контракт: `make verify` — быстрый маршрут по умолчанию, `make test-scripts` — прямое каноническое полное обнаружение тестов, `make verify-full` — альтернативный сводный полный маршрут. Для одного заявления о полной проверке используйте один из полных маршрутов, никогда не оба.

## Правила изменений

- Идентификаторы и команды оставляйте на английском. Документацию для пользователей пишите на языке, который подходит её читателям.
- Различайте текущие доказательства и исторический контекст.
- Для нового плана, ревью, отложенной задачи, предложения по процессу, адресного пакета или запроса в Planveyor берите подходящий шаблон.
- В передачах работы и ревью называйте точные пути и диапазоны ревизий.
- Конфигурацию `target-local`, учётные данные, подробности приложения и правила проекта sibling держите вне корневого корпуса этого репозитория.
- Не добавляйте секреты, токены, cookies, имена внутренних хостов, личные пути, данные учётных записей и скопированные тексты чужих промптов. Где нужно, ставьте `<REDACTED>` или нейтральную заглушку.
- Сгенерированные индексы считайте производными представлениями. Пересобирайте их генератором, который для них описан, и не правьте старые строки вручную.
- Документ с русской копией `name.ru.md` меняется вместе с копией, в том же изменении. Пары перечислены в `i18n/pairs.json`, термины — в `i18n/terms.md`. Когда обе версии обновлены, обновите отметку сверки: `python3 scripts/i18n_pairs.py stamp <copy>`.

## Проверка

`make doc-lint` предупреждает об отставшем переводе. В CI команда `bash scripts/run_doc_lint.sh --i18n-strict` считает отставание ошибкой. Перед обновлением отметки сверки исправьте обе версии и проверьте их смысл.

Сначала запустите самые узкие подходящие проверки, затем проверки документации и жизненного цикла, которых требует изменённый контракт. Установленную команду найдите через `planveyor_help` и затронутый плейбук. Если команда и её результат важны для приёмки, укажите их в файле ревью.

Новый или изменённый публичный артефакт перед запросом ревью проверьте ещё и на ссылки на исходный репозиторий, личные пути и устаревшие исторические доказательства.

## Требования к ревью

По ревью должно быть видно:

- чёткие границы задачи;
- план или другая запись, на которой основано решение;
- проверки, выполненные на текущем содержимом файлов;
- оставшиеся ограничения или ответственный за отложенные задачи;
- следующий допустимый шаг жизненного цикла.

Если работа выявила более широкие потребности в проектировании или упаковке, запишите отложенную задачу с чёткими границами и не расширяйте изменение молча.

## Предложить изменение из sibling

Sibling не правит файлы Planveyor. Напишите предложение в sibling как запрос по шаблону `docs/upstream_packets/_template.md`, проверьте его и закоммитьте там же. Затем отправьте его как issue на GitHub через `gh`. Установить `gh` и войти в нём в свою учётную запись нужно самостоятельно. Файл запроса становится текстом issue (`gh issue create --body-file <файл запроса> --repo planveyor/planveyor`). Порядок действий описан в разделе «Предложить изменение Planveyor» [руководства по sibling](docs/guides/stack-sibling.ru.md#предложить-изменение-planveyor). Принятое изменение возвращается в sibling как обновление контракта Planveyor с извещением в `docs/contract_notices/`.
