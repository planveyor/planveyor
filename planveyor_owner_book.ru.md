# Краткое руководство Owner

[English](planveyor_owner_book.md) · **Русский**

Основной путь для проекта под свой стек — [постоянное руководство по sibling](docs/guides/stack-sibling.ru.md). Оно ведёт от нового каталога до принятой адаптации и полезных задач одной группой `planveyor sibling`:

```sh
planveyor sibling init ~/my-stack
```

Затем в каталоге проекта проведите план в одном из [двух режимов](docs/guides/stack-sibling.ru.md#два-режима-работы-с-планом). В режиме TUI, основном пути: скилл плана → ответы на открытые вопросы плана через `answer`, если они есть → новая сессия Manager командой `planveyor_manager_init` → включение запросов одобрения команд: `/permissions` в окне `planveyor_manager_resume` → одно окно Manager, `planveyor sibling tui`, на весь план, где те же роли делают работу и закрытие документов, а Architect коммитит после вашего одобрения: реализацию и, если закрытие этого требует, документы. В ручном режиме в консоли: скилл плана → `architect` → реальные ответы через `answer` → `run` → просмотр через `close` → разрешённый `close --commit`. После коммита плана отдельный `run` закрывает документы; новый просмотр и, если документам нужен коммит, `--commit` принимают именно подготовленные изменения документов. `ready` проверяет контракт, выбранный план и закрытие; живые проверки стека остаются частью принятого плана.

## Среда и фасад

Из физического корня Planveyor прямой вызов — `./bin/planveyor`. В подготовленной среде его публичный исполняемый файл доступен в `PATH` как `planveyor`. Физический путь фасада определяет копию Planveyor, из которой идут команды; `git` и `HEAD` проверяются до первого действия. Нужен подготовленный поддерживаемый Python; Planveyor не устанавливает зависимости и не переписывает настройки командной оболочки. Для выбранных живых команд ролей и Manager нужен настроенный авторизованный клиент.

Справка `planveyor sibling --help`, `planveyor_entry_doctor` и `planveyor_runtime_info` — диагностика. Doctor и указатель выбранного плана не подтверждают приёмку задачи и не разрешают коммит, вызов роли, обновление или публикацию. Для низкоуровневой команды другого проекта явный `--project` стоит перед именем команды. У группы `sibling` физический проект выводится из текущего каталога; `init` получает новый путь от вас, `upgrade` запускается из внешнего каталога с явно выбранным проектом.

## Решения владельца

Вы выбираете проект, задачу, стек, целевую dev-среду, учётные данные и допустимый режим живой работы. Architect задаёт вопросы; только ваши фактические ответы попадают в журнал. Код стека, проверки и локальные правила принадлежат sibling. В публичный корпус документов не записывают закрытую конфигурацию, секреты и пути вашей машины.

Перед `close --commit` просмотрите текущий точный набор файлов. Сам флаг подтверждает этот коммит; зелёный результат подготовки такого разрешения не даёт. Версия исходников, сессии ролей, отметки времени и технические хеши определяются механизмом. Push, развёртывание и отправка публичного issue требуют отдельного вашего решения.
