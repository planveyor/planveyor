# Sibling под свой стек

[English](stack-sibling.md) · **Русский**

Sibling — отдельный Git-репозиторий для вашего кода, планов и правил стека. Движок Planveyor остаётся во внешней копии Planveyor. Это руководство ведёт от создания проекта до первой полезной задачи, а затем применяется к каждой следующей задаче.

Основные команды — `planveyor sibling …`. Они определяют проект по текущему каталогу, берут выбранный план и проверяют действующую версию движка. Вы выбираете задачу, отвечаете на вопросы ролей и подтверждаете коммиты.

## Один раз: среда и создание проекта

Первая версия поддерживает macOS. Нужны Git, zsh, rg и подготовленное окружение с Python 3.12, Copier 9.18.2 и PyYAML в версиях из `requirements-dev.lock`. Python 3.12 должен стоять первым в `PATH`, в том числе в login shell: в нём роли выполняют команды, а обвязка стека может вызывать голый `python3`. Временный каталог `TMPDIR` должен существовать и лежать вне Git-репозитория. Как это проверить, сказано в разделе [«Поддерживаемая среда»](launch-and-role-modes.ru.md#поддерживаемая-среда) руководства запуска.

Для работы ролей нужен авторизованный Codex CLI с настроенными ролями. Их модели задаёт ваша конфигурация Codex: Codex home или проектный каталог `.codex/`. Planveyor эту конфигурацию не создаёт и не показывает, поэтому перед первым запуском отметьте время, а после него проверьте, какие модели применились. Всё это описано в разделе [«Настройка Codex»](launch-and-role-modes.ru.md#настройка-codex).

Инструменты и dev-среду своего стека вы готовите отдельно. Начинайте адаптацию на свежей пустой dev-цели и пересоздавайте её перед каждым повтором с нуля: остатки прошлых прогонов порождают у ролей ложные вопросы. Если предпосылки не хватает, команда её назовёт, но устанавливать или настраивать её автоматически Planveyor не будет.

В подготовленном терминале откройте каталог выбранной копии Planveyor без незакоммиченных изменений. `init` и `upgrade` проверяют это сами, отдельная команда Git не нужна. Если `planveyor` уже доступен в `PATH`, следующий шаг пропустите. Иначе сделайте команду доступной в этой вкладке:

```sh
export PATH="$PWD/bin:$PATH"
```

Эта строка берёт текущую копию Planveyor и не меняет настройки оболочки. В новой вкладке в `PATH` нужна та же выбранная копия. Прямой вызов из её корня — `./bin/planveyor`, отдельный установщик команд не нужен.

Команды можно выполнять в своём терминале или поручить агенту в чате Codex. Песочницу чата задаёт папка, в которой он открыт, и песочница может не дать команде записать нужные файлы: `architect` и `run` пишут сессии ролей в Codex home, а `init` и `close --commit` пишут в `.git`. Для `init` откройте чат в родительском каталоге нового проекта, для остальных команд — новый чат в корне проекта. Доступ сверх песочницы для конкретной операции разрешаете вы. При отказе читайте сообщение команды: `planveyor sibling` возвращает код 3 и при обычных отказах своих проверок, поэтому код 3 сам по себе не доказывает, что не хватило доступа.

Выберите каталог нового проекта. В примере это `~/my-stack`, замените в нём только имя проекта:

```sh
planveyor sibling init ~/my-stack
cd ~/my-stack
```

Родительский каталог должен существовать. Сам каталог лежит вне копии Planveyor, а путь к нему проходит через обычные каталоги, без символических ссылок. Имя начинается с латинской буквы или цифры и содержит только буквы, цифры, `.`, `_` и `-`. Имя `default` недопустимо. Если проект уже существует и не пуст, команда оставляет его как есть и отказывает в `init`.

`init` сам берёт версию выбранного движка, делает первый коммит с вашими именем и email из Git и закрепляет их для следующих коммитов этого sibling. Если имя и email в Git ещё не настроены, задайте эту пару явно:

```sh
planveyor sibling init ~/my-stack --author-name "Your Name" --author-email "you@example.invalid"
```

После успешного создания команда проверяет контракт и сообщает результат. План и заполненную анкету `init` ещё не создаёт.

## Адаптация под ваш стек

Откройте sibling в обычном чате Codex или ZCode. Скиллы уже лежат в `.agents/skills/`, отдельно их устанавливать не нужно. В Codex скилл называется `$planveyor-plan-draft`, в ZCode — `/planveyor-plan-draft`.

Отправьте в чат:

```text
$planveyor-plan-draft Создай и сделай текущим план адаптации sibling под мой стек по docs/_template_stack_brief.md. Создай docs/stack_brief.md как вход плана. Задай вопросы по неподтверждённым решениям. Следующую полезную задачу согласуем отдельно.
```

Добавьте в то же сообщение известные вам факты о стеке. По ним скилл и Architect заполняют анкету: чем полнее факты, тем меньше вопросов задаст Architect. Удобно собрать их по десяти разделам шаблона анкеты, который лежит в sibling и назван в запросе. Разделы шаблона подсказывают, что написать и когда фактов достаточно («Достаточно, если»):

1. назначение проекта и чем проверяется готовность его среды;
2. стек и версии инструментов, где они закреплены, запрещённые возможности;
3. что уже стоит у разработчика и что ставит `make setup`;
4. живая цель: dev-среда, её маркер и проверка цели до записи;
5. файл с учётными данными и имена ключей, без значений;
6. команды стека: нужна ли каждой сеть или живая цель, кто её запускает, коды выхода;
7. чем доказывается результат: формат и место отчёта тестов;
8. правила для ролей;
9. кто запускает живые цели: роли с сетью или человек;
10. что вне объёма.

Пример такого блока для SQL Server — раздел 6 руководства в репозитории `planveyor-mssql`.

Скилл создаёт план и анкету. В границы задачи плана (раздел `## Scope`) входят обвязка стека, корневой `README.md` проекта и локальные правила ролей. Код в этих границах затем реализует Coder.

Скилл использует выбранный доверенный фасад из окружения запуска. Если приложение не видит команду `planveyor` и ему не передан `PLANVEYOR_RUNTIME_ROOT`, оно один раз попросит выбрать копию Planveyor с движком. Не записывайте этот путь в публичные планы и правила стека.

Проверьте, какой план выбран. Это можно сделать в любой момент:

```sh
planveyor sibling plan
```

Команда печатает план, его статус и следующий шаг. Скилл может создать план и оставить указатель плана без изменений. Если план ещё не выбран, команда завершается с кодом 3 и сообщением «Текущий plan не выбран или pointer повреждён. Выполните planveyor sibling plan docs/plans/NAME.md.». Если указатель остался на прошлом плане, команда покажет прошлый план. В обоих случаях выберите созданный план по пути из ответа скилла:

```sh
planveyor sibling plan "docs/plans/<plan>.md"
```

Команда не выбирает задачу по последней дате файла.

Начните обсуждение с Architect:

```sh
planveyor sibling architect
```

Команда печатает ответ Architect, а в конце — план, статус и строку «Следующий шаг: …». Действует последняя такая строка. В выводе встречаются и такие строки:

```text
- Next: Owner
- Open items: (to=Owner, needs_owner=yes) Provide `PLAN_PATH`
```

Это постоянная концовка первого хода роли: сессия сначала получает вводную без плана, а план фасад передаёт следующим сообщением. Делать по этим строкам ничего не нужно.

Если Architect задал вопросы, прочитайте их и предложенные варианты. Передайте свой ответ:

```sh
planveyor sibling answer
```

Если вопросов несколько, команда покажет их id. Например, ответ на показанный вопрос `Q2`:

```sh
planveyor sibling answer Q2
```

Ответ вводите обычным текстом, формат журнала и время команда оформит сама. Пустой ввод и отмена не подтверждают предложенный вариант. Сохранив ответ, команда печатает «Ответ сохранён. Следующий шаг: planveyor sibling architect» или ту же строку с `run`. Выполните напечатанный шаг. Пока план в статусе `Architect initial draft`, ответ ждёт следующего хода Architect, и второй `answer` до этого хода откажет с сообщением «Уже есть ожидающий Owner payload. Завершите соответствующий ход роли; существующие ответы сохранены.». Поэтому на несколько вопросов в этом статусе отвечайте по одному и после каждого ответа выполняйте напечатанный шаг, `planveyor sibling architect`. Ответы по умолчанию на частые вопросы собраны в разделе [«Типовые вопросы Architect»](#типовые-вопросы-architect).

Повторяйте обсуждение, пока Architect не согласует нужные решения. Дополнительные полномочия роли и условия приёмки требуют вашего явного решения. Когда развилок для Owner не остаётся, Architect сам переводит план в статус `Architect draft`, и следующим шагом становится `planveyor sibling run`. Подтверждения Architect при этом не просит: конвейер рассчитан на работу без человека.

### Раздел «Как я понял задачу»

Раздел `## Как я понял задачу` есть в плане всегда. Прочитайте его после `planveyor sibling architect` и до `run` и сверьте с поручением и анкетой. Вывести раздел можно так:

```sh
awk '/^## Как я понял задачу/{p=1; print; next} p && /^## /{exit} p' "docs/plans/<plan>.md"
```

Если раздел расходится с поручением, не запускайте `run`. После перехода в `Architect draft` первая версия не даёт штатно поправить раздел: `answer` без открытого вопроса в этом статусе отказывает с кодом 3 и сообщением «Открытых Owner вопросов нет.».

Чтобы подтвердить раздел самим, допишите в запрос скиллу: «До перевода плана в Architect draft покажи мне раздел «Как я понял задачу» и дождись подтверждения». Обычно Architect тогда открывает вопрос, и вы подтверждаете раздел через `planveyor sibling answer`. Так ведёт себя модель, движок этого не гарантирует.

Если команды выполняет агент, попросите его выводить раздел в чат перед каждым `run`. В интерактивном режиме Manager (`planveyor_manager_collab_tui`, см. [роли и входы](launch-and-role-modes.ru.md#роли-и-входы)) вы говорите с Manager напрямую и можете попросить его вывести раздел при переходе к Planner. В этом режиме действует `COMMIT_POLICY=native_existing`: закрытие и коммит выполняет сам Architect, без `close --commit`. Вы не видите коммит заранее, и в этом главное отличие от `planveyor sibling run`.

## Типовые вопросы Architect

Architect спрашивает, когда в анкете или плане не хватает решения, и обычно сразу предлагает ответ. Ниже собраны ответы по умолчанию на частые вопросы адаптации и обычной задачи. Они подходят для любого стека: подставьте в ответ факты своего стека из анкеты и поручения.

Проход может вести агент по вашему поручению. Тогда он отвечает по этой таблице и пишет в ответе, что отвечает по поручению Owner. Решения, уже принятые в анкете и плане, он не пересматривает и не согласует заново. Остальные вопросы он возвращает вам, их список — под таблицей.

| Вопрос | Ответ по умолчанию | Что подставить |
|---|---|---|
| Путь к движку Planveyor (спрашивает скилл) | Путь к вашей копии Planveyor, из которой идут команды. В публичные планы, правила и README он не попадает. | Путь к вашей копии |
| Подтвердить раздел «Как я понял задачу» | Перечитать текущий текст раздела. Подтвердить, если он совпадает с анкетой и поручением и не добавляет работы сверх границ задачи. Иначе назвать расхождение и попросить исправить. В адаптации следующая полезная задача остаётся отдельным поручением. | Назначение проекта и проверку готовности его среды |
| Поле анкеты с предложенным ответом | Принять, если предложение выполняет условие «Достаточно, если» из этого раздела шаблона анкеты. Иначе дополнить до этого условия. | Факты своего стека |
| Версии инструментов | Взять версии, которые уже установлены и закреплены в файлах проекта. Новые версии не выбирать. Отсутствующий инструмент назвать как предпосылку. | Инструменты и файлы, где закреплены версии |
| Какое окружение использовать для команд проекта | Уже подготовленное окружение через `PATH` текущего процесса, фактическую версию проверяет обвязка стека. Системные инструменты не устанавливать: зависимости проекта ставит только согласованный в анкете `make setup`, а их кэши лежат в `.tmp/`. Не менять настройки оболочки, `HOME` и конфигурацию Codex. Личные пути не писать в план, README и правила. | Интерпретатор или SDK вашей среды |
| Как убедиться, что запись идёт в dev-среду | Код проверяет согласованный маркер назначенной dev-среды до каждой записи. Нет маркера — отказ без записи. Сервер, маркер и учётные записи роли не меняют. | Маркер и способ его проверки в вашем хранилище |
| Проверять наличие маркера или его значение | Только наличие. Значение задаёт администратор, обвязка его не читает. Новое значение, например `value=1`, не вводить. | Запрос проверки маркера в вашем хранилище |
| Где параметры подключения | `.env.local` с правами 0600, в `.gitignore`, не отслеживается Git. В план и README попадают только имена ключей. | Имена ключей |
| Какие команды допустимы | Цели стека из анкеты. У каждой указано, нужна ли сеть или живая цель, кто её запускает, ожидаемый код выхода и отчёт. | Цели `make` вашего стека |
| Нужна ли отдельная офлайн-цель для тестов обвязки | Да: офлайн-тесты обвязки получают свою цель, например `make test`, и работают без сети и живой цели. Анкету и план синхронизировать, реализует цель Coder. | Цель и файл офлайн-тестов |
| Кто запускает живые цели | Роли в песочнице с сетью, если сеть у выбранного Codex home уже настроена. Иначе оператор-человек. Сеть агент сам не включает. | Цели и роли, которые их запускают |
| Условия приёмки | Принять, если каждое условие называет свой тест и проверяет результат, входы и выходы, которые требует поручение. Недостающий отрицательный или граничный случай добавить. Новых требований сверх поручения не вводить. | Тесты вашего фреймворка |
| Чем доказать результат | Отчётом текущего прогона на ревьюируемых байтах. Reviewer повторяет проверку сам, а при варианте «только оператор» её по запросу Reviewer повторяет оператор. Старый зелёный результат и отчёт другой задачи не переносятся. | Формат и место отчёта тестов |
| Технический вопрос обвязки: API, формат, сборка, разбор вывода | Это не решение Owner. Роли решают его по документации инструмента и фактам анкеты, не меняя границы задачи, права и приёмку. Если исправление требует изменить что-то из этого, роль возвращает вопрос с вариантами. | Документацию инструментов стека |
| Переделать обвязку по-другому или «лучше» | Нет. Решения анкеты и уже работающие части сохраняются. Новое проектирование допустимо только при доказанном отказе нынешнего способа, причину записывают в план. | — |
| Внешние модели или MCP как часть процесса | Нет: процесс использует только штатные средства Planveyor. Требование внешних моделей и их квитанций снимается. | — |
| Найдена открытая отложенная задача по той же теме | Сослаться на неё в `Context links` плана и оставить её запись без изменений. Обычная задача не требует её продвижения. | Ссылку `source_ref#item_id` |
| Что за границами задачи | Production, бизнес-данные, конфигурация сервера, CI и другие ОС, если поручение не говорит иначе. | Исключения вашего проекта |

Агент возвращает вам вопрос, если он касается:

- значений секретов (агент может только проверить права файла);
- production, бизнес-данных или цели без маркера dev-среды;
- прав администратора, изменения сервера, маркера или учётных записей;
- расширения границ задачи сверх поручения и анкеты, смены стека или версий;
- включения сети, изменения конфигурации Codex, `HOME` или выбранного движка;
- публикации: remote, push, issue, видимость репозитория;
- коммита, на который нет вашего прямого разрешения в этой сессии;
- решения, которого нет ни в анкете, ни в поручении, ни в этой таблице.

Ответ из таблицы не заменяет проверок. Красный результат возвращает работу роли. Подтверждение раздела «Как я понял задачу» не разрешает коммит.

## Провести план

Перед первым `run` на месте должно быть всё, что роли сами не делают. Это ваша часть работы, агент в чате поможет её подготовить:

- среда из раздела [«Один раз: среда и создание проекта»](#один-раз-среда-и-создание-проекта): Python 3.12 первым в `PATH`, в том числе в login shell, и `TMPDIR` вне Git;
- Codex CLI с выполненным входом и ролями Manager collab в выбранном Codex home или в проектном каталоге `.codex/`, см. [«Настройка Codex»](launch-and-role-modes.ru.md#настройка-codex); проектный каталог Codex применяет только в доверенном проекте, см. [«Проектный каталог `.codex/`»](launch-and-role-modes.ru.md#проектный-каталог-codex);
- отметка времени для проверки моделей, поставленная до запуска, см. [«Проверка фактических моделей»](launch-and-role-modes.ru.md#проверка-фактических-моделей);
- сеть в песочнице Codex home, если живые цели по анкете запускают сами роли;
- файл с учётными данными, если они нужны стеку;
- свежая dev-цель с маркером назначенной dev-среды и правами, которые согласованы в анкете.

Подробнее об учётных данных и доступе к dev-среде — в двух следующих абзацах.

Если стеку нужны учётные данные, имена ключей и защищённый файл называет анкета, а после адаптации — локальный `README.md`. Введите значения в локальном редакторе: в чат, планы и отчёты секреты не передаются. У `.env.local` должны быть права 0600, Git должен его игнорировать и не отслеживать. Файл читает обвязка, а роли вызывают только принятые команды стека. Администратор готовит dev-среду с нужными маркерами и правами, а обвязка должна проверять её до записи.

Если ролям нужен доступ к dev-среде, согласуйте в анкете один вариант: сеть у выбранного Codex home или живые команды, которые выполняет человек. Если живые цели запускают сами роли, им нужна сеть в песочнице. Её включают в конфигурации Codex home до первого `run`, см. раздел [«Доступ к dev-среде»](launch-and-role-modes.ru.md#доступ-к-dev-среде) руководства запуска. Planveyor сам не открывает сеть и не меняет Codex home. Если живые команды выполняет только оператор, роль остановится с конкретной командой. Когда её выполнят, передайте фактический результат через `answer`. Красный результат требует исправления и повторной проверки.

Когда первичный разбор задачи с Architect (intake) завершён, запустите Manager в режиме collab:

```sh
planveyor sibling run
```

Manager ведёт роли Architect, Planner, Coder и Reviewer по статусу плана. Команда сама готовит нужные сессии: запоминать их id или обновлять их после коммита не нужно. Как и после `architect`, действует последняя строка вывода «Следующий шаг: …».

Если Manager ждёт вашего решения, выполните `planveyor sibling answer`, а затем следующий шаг, который напечатает эта команда. Если Manager достиг лимита шагов, повторите тот же `run`. Ошибка проверки возвращает работу нужной роли, и согласие с прежним зелёным результатом её не заменяет.

При адаптации роли создают обвязку стека, его проверки и правила. Правила лежат в двух локальных разделах восьми файлов, и обновление сохраняет именно эти разделы:

| Роль или фаза | Файл |
|---|---|
| Architect | `docs/tools/prompts/architect_status_driven.md` |
| Planner | `docs/tools/prompts/planner_status_driven.md` |
| Coder | `docs/tools/prompts/coder_status_driven.md` |
| Coder: миграции | `docs/tools/prompts/coder_migrations_gate.md` |
| Reviewer | `docs/tools/prompts/reviewer_status_driven.md` |
| Ревью коммита | `docs/playbooks/review_staged_or_commit.md` |
| Ревью диапазона | `docs/playbooks/review_merge_range.md` |
| Аудит после слияния | `docs/playbooks/post_merge_audit.md` |

### Остановить run и продолжить тот же план

Остановка нужна, если работа ходит по кругу: например, ревью в третий раз возвращает Coder замечание на ту же тему. Останавливать ли `run` и продолжать ли потом тот же план, решает Owner.

1. Остановите `run` одним сигналом SIGINT: нажмите Ctrl-C в его терминале. Агент отправляет SIGINT группе процессов этого `run`. Не используйте `kill -9`. Команда завершится с ненулевым кодом, а роль могла не закончить свой ход.
2. Зафиксируйте состояние, ничего не исправляя:

   ```sh
   planveyor sibling plan
   git diff --cached --name-status
   git status --short --untracked-files=all > "$TMPDIR/planveyor-stop.status"
   git ls-files -m -o --exclude-standard -z | xargs -0 shasum -a 256 > "$TMPDIR/planveyor-stop.sha256"
   ```

   Индекс должен быть пуст: `git diff --cached` ничего не выводит. Две последние строки сохраняют полный список изменённых и новых файлов и их контрольные суммы. Флаг `--untracked-files=all` перечисляет каждый новый файл, а не только его каталог.
3. Решите, оставить остановку или продолжить тот же план.
4. Перед продолжением убедитесь, что файлы не менялись:

   ```sh
   git status --short --untracked-files=all > "$TMPDIR/planveyor-continue.status"
   diff "$TMPDIR/planveyor-stop.status" "$TMPDIR/planveyor-continue.status"
   shasum -a 256 -c --quiet "$TMPDIR/planveyor-stop.sha256"
   planveyor sibling plan
   ```

   `diff` ничего не выводит, если список файлов тот же, а `shasum` — если совпали все суммы. Так видны и новые файлы внутри новых каталогов. `plan` показывает прежний план и его следующий шаг. Выполните этот шаг, обычно это тот же `planveyor sibling run`: Manager продолжит работу по статусу плана.

План, ревью, статусы и квитанции при остановке не правьте. Новый план ради продолжения не создавайте.

## Коммит и закрытие документов

Когда Architect принял итоговое ревью и Manager предлагает закрытие, сначала посмотрите, что подготовлено:

```sh
planveyor sibling close
```

Этот вызов показывает состояние и будущий набор файлов, а статус, индекс и сессии не меняет. Если план готов к коммиту, первая строка вывода — «План принят. Следующий шаг: planveyor sibling close --commit.», за ней идут список файлов и строка «Сообщение коммита: …». Открытый вопрос или обязательная проверка остановит подготовку и назовёт следующий шаг. Прочитайте показанный набор и сообщение, проверьте его изменения в редакторе. Если после просмотра файлы правили, повторите просмотр. Только после этого разрешите конкретный коммит:

```sh
planveyor sibling close --commit
```

Флаг `--commit` — ваше явное подтверждение закоммитить проверенный текущий набор, дополнительный общий «yes» не нужен. Команда ещё раз проверяет готовность, переводит принятый план в `Done` и коммитит только его точный набор файлов. Чужие файлы в индексе, неготовое или устаревшее ревью и ошибки текущих проверок означают отказ. Скрытого разрешения на коммит роли не получают.

Приёмку Architect команда `close` читает в файле ревью. В нём должен быть ровно один раздел `## Архитектурное ревью` (или `## Arch review`), и его первая непустая строка — «Вердикт: принято.». Заголовок из шаблона, `## Архитектурное ревью (Architect; optional)`, не подходит: пояснение в скобках Architect убирает. Иначе `close` ответит «Нужна одна секция «Архитектурное ревью» в review artifact. Следующий шаг: planveyor sibling architect.» или «Первый вердикт Architect не даёт однозначной приёмки…». Выполните `planveyor sibling architect`, затем снова `close`. Это технический возврат к Architect, ответ Owner не нужен.

После коммита плана команда печатает «План закоммичен. Следующий шаг: planveyor sibling run для документов.». Закрытие документов — отдельный ход Manager:

```sh
planveyor sibling run
planveyor sibling close
```

Если документам нужен отдельный коммит, `close` напишет «Документы готовы. Следующий шаг: planveyor sibling close --commit.» и покажет их набор. Просмотрите его и выполните `planveyor sibling close --commit`: это ваше отдельное подтверждение уже показанного набора. Первый `--commit` не запускает роли и не подтверждает документы, которых ещё нет. После коммита документов команда сразу проверяет закрытие. Если обязательство осталось, повторите указанный шаг.

Работа закончена, когда команда напечатает «План и документы закрыты. Можно начать следующую задачу.». Пока закрытие не завершено, `close` может завершиться и с кодом 0, но напечатать другой текст, например «Документы ещё не закрыты: <reason>. Следующий шаг: planveyor sibling run.». Смотрите на текст, а не только на код выхода. Другие незавершённые состояния `close` сообщает отказом с кодом 3, например «Нет однозначного receipt-owned docs bundle; следующий шаг: planveyor sibling run.». Один статус `Done`, первый коммит или успешный doctor ещё не означают, что весь шаг завершён. Если циклов закрытия несколько, команда попросит указать нужный цикл: произвольный каталог она не выбирает. Отдельный аудит после слияния может оставаться открытым, если так предусмотрено планом.

## Следующая задача и готовность

Перед следующей задачей проверьте, что текущая закрыта:

```sh
planveyor sibling ready
```

Команда проверяет контракт, состояние выбранного плана и закрытие его документов. Готовность подтверждает только итог «Consumer contract и выбранный план закрыты. Готовность отдельного release или SQL не проверялась.». Другой текст, например «Выбранный план ещё не закрыт. Следующий шаг: planveyor sibling run.», команда тоже печатает с кодом 0: задача не закончена, выполните напечатанный шаг. Живые проверки вашего стека Coder и Reviewer выполняют по принятой анкете и плану, `ready` их заново не запускает. Сверьте фактические результаты приёмки: старый отчёт или отчёт другой задачи их не заменяет. Этот итог не означает ни публикации, ни выполненного отдельного аудита после слияния, ни разрешения писать в production.

Когда `ready` подтвердил, что адаптация закрыта, отправьте в том же чате:

```text
$planveyor-plan-draft Создай и сделай текущим обычный план по моему прямому поручению: <result and observable check>. Покажи matching open follow-up, сохрани его неизменным и добавь source_ref#item_id в Context links.
```

Опишите желаемый результат. Адаптация согласует назначение и готовность стека, а следующая полезная задача — отдельное прямое поручение Owner.

Скилл проверит, нет ли открытой отложенной задачи на ту же тему, и сошлётся на неё в плане, не меняя её. Правила этой проверки — в разделе [«Если проход ведёт агент»](#если-проход-ведёт-агент).

Скилл может оставить указатель на прошлом плане. Проверьте выбор командой `planveyor sibling plan` и при необходимости выберите новый план по пути из ответа скилла, как при [адаптации](#адаптация-под-ваш-стек).

Повторите цикл: `architect`; на каждый вопрос `answer` и напечатанный им шаг, обычно снова `architect`; затем `run` → `close` → отдельный `close --commit`; для документов `run` → `close` → при показанном обязательстве отдельный `close --commit`; в конце `ready`. Перед следующей задачей завершите закрытие документов текущей. Эта последовательность описывает ожидаемые шаги, а не уже выполненный проход.

Для большой задачи остаются обычные маршруты [анализа](../playbooks/analysis_wave.md) и [декомпозиции](../playbooks/decomposition_wave.md). Попросите скилл плана выбрать вместе с Architect подходящий тип плана. Отдельные низкоуровневые точки входа и очередь описаны в руководстве [«Запуск и режимы ролей»](launch-and-role-modes.ru.md). `sibling run` работает с выбранным планом и сам очередь не создаёт.

## Вернуться к работе в существующем sibling

Sibling работает с той версией движка, на которой он закреплён. Если вы продолжаете работу в уже созданном sibling, например в клоне готового примера или на другом компьютере, сначала выберите эту версию и только потом начинайте новую задачу.

1. В корне sibling посмотрите закреплённую версию: это значение поля `source_commit`.

   ```sh
   cat docs/_meta/planveyor_contract_authority.v1.json
   ```

2. Переключите свою копию Planveyor без незакоммиченных изменений на эту версию и сделайте её команду доступной в этой вкладке. Вместо `<Planveyor checkout>` подставьте путь к копии, вместо `<version>` — значение `source_commit`:

   ```sh
   git -C <Planveyor checkout> switch --detach <version>
   export PATH="<Planveyor checkout>/bin:$PATH"
   ```

   Версия должна быть доступна на ветке или теге этой копии. Если её там нет, сначала получите её обычным `git -C <Planveyor checkout> fetch`.
3. Проверьте, что версии совпали:

   ```sh
   planveyor --project "$PWD" planveyor_consumer_doctor
   ```

   При совпадении команда завершается с кодом 0, в её выводе `"state": "ok"`, а `source_commit` и `runtime_commit` равны. Если версии разные, код выхода 3, `state` равно `blocked`, а в `problems` есть строка `runtime commit … differs from contract …`. В этом случае и `planveyor sibling ready` не подтвердит готовность: он напечатает «Consumer contract требует разбора; готовность не подтверждена.». Если в копии нет этой версии, команда тоже завершится с кодом 3 и назовёт причину в поле `reason`.

Чтобы перейти на более новую версию Planveyor, сначала закончите и закройте текущую задачу, затем выберите новую копию и проведите обновление по разделу [«Получить новую версию Planveyor»](#получить-новую-версию-planveyor). Новую задачу начинайте после закрытия плана обновления.

## Получить новую версию Planveyor

Sibling закрепляет конкретную версию движка: роли, шаблоны и проверки работают по одним правилам, и результат можно воспроизвести. Эту версию и технические идентификаторы команды получают сами. Новую копию движка сначала выбираете вы, а обновление sibling проходит отдельным обычным планом.

Обновите установленную копию Planveyor своим обычным способом. Команда `sibling upgrade` не делает скрытого pull и не переключает ветку Git. Выбранная версия должна продолжать прежнюю историю и быть доступна на ветке или теге. Доведите и закройте текущую работу, сохраните изменения, завершите активные сессии и выйдите из каталога sibling: `upgrade` меняет каталоги местами.

Из внешнего каталога выберите ваш проект:

```sh
planveyor --project ~/my-stack sibling upgrade
```

При успешном обновлении команда сама получает новую версию, проверяет, что локальные правила сохранились, и печатает пути к резервной копии и к плану обновления. Извещения входят в этот план, но отдельно команда их не выводит. Она создаёт план обновления и выбирает его. Откройте sibling заново и проведите этот план тем же циклом `architect` → `run` → `close`. Сообщение об обновлённом контракте ещё не означает, что адаптация принята.

В выводе `sibling upgrade` этот же план называется «план адаптации» или «adaptation plan». В руководстве он назван «планом обновления», чтобы отличать его от первого плана адаптации нового sibling под стек.

Если обновление остановилось с кандидатом, исходный sibling остаётся на месте, а резервная копия и план обновления ещё не созданы. Нынешняя обёртка возвращает код 3 и скрывает stdout с путём к кандидату и списком проблем, сообщения stderr остаются видимыми. Кандидат лежит рядом с проектом в `.<name>-upgrade-<first 12 characters of the new commit>`. Повторный запуск той же команды назовёт точный путь сообщением `candidate path already exists: …`.

Откройте каталог кандидата в обычном чате агентного харнеса. Попросите разобрать его фактический `git status`, файлы `.rej`, маркеры `<<<<<<<` и изменения локальных разделов, проверить точный diff и сохранить принятый результат в кандидате. После настоящего ревью и коммита в кандидате примите его из внешнего каталога:

```sh
planveyor --project ~/my-stack sibling upgrade --accept-candidate
```

Выбранная версия движка должна остаться той же. Потеря локальных разделов, неоднозначное переименование, битое извещение или занятый путь резервной копии требуют отдельного разбора. Обходным путём команда их не исправляет. Резервная копия содержит полную копию проекта, включая учётные данные и локальное состояние. Храните её только у себя и удалите сами, когда адаптацию примут.

## Предложить изменение Planveyor

Правила своего стека вы меняете в sibling. Общую проблему движка или процесса передают в Planveyor запросом (upstream request). Это второй публичный сценарий обмена: предложение из sibling, решение в исходном репозитории и возврат исправления через обновление.

В обычном чате sibling попросите подготовить запрос по шаблону `docs/upstream_packets/_template.md`: симптом, пробел процесса, предлагаемое исправление и ссылки на вашу задачу и на место, где нашли проблему. Факты своего стека вынесите в раздел `Target-Specific Facts To Filter`. Секреты, адреса серверов и абсолютные пути в запрос не входят. Подготовленный запрос проходит проверку и ваше ревью. Просьба подготовить файл ещё не разрешает его отправку.

Когда запрос принят и закоммичен, отдельно разрешите отправку issue. Для этого нужны установленный и авторизованный GitHub CLI `gh` и обычная команда `gh issue create --body-file <файл запроса> --repo planveyor/planveyor --title "<тема запроса>"` с точным подготовленным файлом. Флаг `--repo` обязателен: без него `gh` берёт репозиторий из remote текущего каталога, то есть из вашего sibling, а без remote останавливается. Попросите агента показать готовую команду и публичный текст issue. Переносить текст вручную и подставлять технические id не нужно. Если `gh` не настроен, отправка остановится и назовёт недостающую предпосылку. Созданный issue сам по себе не означает, что предложение принято.

Сопровождающий Planveyor принимает запрос штатными командами исходного репозитория `planveyor_upstream_request_import` и `planveyor_upstream_request_ack`. Они работают только в физическом корне исходного репозитория, из sibling их не запускают. Решение и исправление проходят обычный план в исходном репозитории. Изменение контракта или поведения сопровождает извещение в `docs/contract_notices/` с проверками и действиями для sibling.

После публикации выбранной версии выполните `sibling upgrade`. Созданный план обновления включает извещение и обновление локальной копии запроса. Роли проверяют результат на вашем стеке. Завершите оба коммита и закрытие документов. Формат пакетов и низкоуровневые команды чтения состояния описаны в руководстве [«Жизненный цикл и пакеты»](lifecycle-and-packets.ru.md).

### Пример: SQL Server sibling → исправление provenance → обновление

Это условный обмен после публикации версии, а не отчёт об уже отправленном issue. Допустим, в `planveyor-mssql` запись о происхождении плана (provenance) теряет id текущего чата при вызове фасада. SQL Server и tSQLt объясняют, где нашли проблему, а передача контекста чата — общая механика Planveyor.

Попросите подготовить запрос по шаблону с настоящими ссылками на план и ревью вашего sibling. Для примера содержание такое:

| Поле запроса | Содержание |
|---|---|
| `origin_repo` | `planveyor-mssql` |
| `requested_source_canon_path` | `bin/planveyor` |
| `symptom` | В записи о происхождении нет id текущего чата после вызова фасада. |
| `process_gap` | Фасад в дочернем процессе теряет контекст вызывающего чата. |
| `suggested_fix` | Передавать id как вход только для записи о происхождении и проверить три случая: значение не задано, пустое и задано. |
| `Target-Specific Facts To Filter` | MSSQL/tSQLt остаются локальным стеком и не становятся умолчаниями движка. |

Подготовьте запрос, проведите его ревью и затем отдельно разрешите отправку issue той же командой `gh issue create --body-file … --repo planveyor/planveyor`. Сопровождающий исходного репозитория импортирует запрос, принимает решение и проводит обычный план исправления. Извещение по [существующему формату](../contract_notices/README.md) включает проверку записи о происхождении через фасад и `planveyor_consumer_doctor`. Действия sibling — проверить собственные SQL-правила и обновить локальную копию запроса. ACK в исходном репозитории (Source-only ACK) фиксирует настоящие ссылки на решение и исполнение и состояние `decided` в исходном репозитории. Сам ACK sibling не обновляет.

После публикации выберите новую версию Planveyor и выполните `sibling upgrade`. В плане обновления Coder проверит запись о происхождении и настоящие проверки вашего SQL-стека, а также сверит поля и ссылки локального запроса с извещением. Это локальное изменение проекта проходит ревью, два точных коммита и закрытие документов. ACK исходного репозитория из sibling не вызывают. Если кандидат обновления заблокирован, сначала разберите настоящую причину. Issue, состояние `decided` в исходном репозитории и успешный запуск Copier не заменяют принятие адаптации.

## Если команда остановилась

| Что сообщает команда | Следующий шаг |
|---|---|
| Нет инструмента, подходящего Python или авторизации | Подготовить названную предпосылку и повторить ту же команду. |
| Не выбран проект или план | Открыть нужный sibling и выбрать созданный план командой `planveyor sibling plan` с его путём. Если задач несколько, выбираете вы. |
| Код 3 или отказ записи в чате агента | Прочитать сообщение: код 3 сам по себе не доказывает, что не хватило доступа. Доступ сверх песочницы для конкретной операции разрешаете вы. |
| Открыт вопрос Owner | `planveyor sibling answer`, затем следующий шаг, который напечатает эта команда. |
| «Уже есть ожидающий Owner payload…» после `answer` | Прошлый ответ ещё не передан роли. Выполните напечатанный тогда шаг, обычно `planveyor sibling architect`, затем отвечайте на следующий вопрос. |
| «Открытых Owner вопросов нет.» после `answer` | Вопроса к вам нет. В `Architect draft` раздел «Как я понял задачу» штатно не поправить, см. [раздел о нём](#раздел-как-я-понял-задачу). |
| Manager достиг лимита шагов | Повторить `planveyor sibling run`. |
| Ревью раз за разом возвращает работу на одну тему | Остановить `run` по шагам из раздела [«Остановить run и продолжить тот же план»](#остановить-run-и-продолжить-тот-же-план). Продолжать ли, решает Owner. |
| Ревью или доказательство устарело | Вернуться к указанной роли: старый зелёный результат не подтверждает новые изменения. |
| Нет единственного раздела «Архитектурное ревью» или его первая строка не «Вердикт: принято.» | Выполнить `planveyor sibling architect`, затем снова `close`. |
| В индексе есть чужие файлы | Разобрать их отдельно: `close` не очищает и не коммитит чужую работу. |
| Требуется коммит | Посмотреть вывод `close`, затем явно выполнить и подтвердить `close --commit`. |
| Документы ещё не закрыты | Выполнить указанный ход Manager или закрытие. Следующую задачу начинать после завершения. |
| «Consumer contract требует разбора; готовность не подтверждена.» после `ready` | Проверить контракт и версию движка командой `planveyor --project "$PWD" planveyor_consumer_doctor`, см. [«Вернуться к работе в существующем sibling»](#вернуться-к-работе-в-существующем-sibling). |
| `ready` завершился с кодом 0, но без итога о закрытии | Задача не закончена: выполнить напечатанный следующий шаг. |
| Версия копии Planveyor, из которой идут команды, расходится с sibling | Выбрать закреплённую версию по разделу [«Вернуться к работе в существующем sibling»](#вернуться-к-работе-в-существующем-sibling) или провести план обновления. |
| После обновления остался кандидат или резервная копия | При коде 3 найти каталог кандидата и разобрать его фактические проблемы по шагам выше. После успеха проверить план обновления и хранить резервную копию, пока план не принят. Исходный sibling вручную не заменять. |

Справку показывает обычная команда `planveyor sibling --help`. Она не запускает роли и не меняет проект.

## Если проход ведёт агент

Этот раздел — для агента, который ведёт проход по поручению Owner. Человеку читать его не обязательно.

### Отложенные задачи при новом плане

Настоящие замечания (findings), найденные при адаптации, проходят штатную запись в отложенные задачи (capture); zero findings допустимы.

Скилл ищет совпадения в ограниченном объёме (bounded discovery). Совпавшая запись (matching row) остаётся без изменений (unchanged): `status=open`, `plan=null`, `disposition_kind=null`, `disposition_ref=null`, `disposition_commit_oid=null`. Точная ссылка `source_ref#item_id` — только контекст плана. Automatic backlink запрещён. Если совпадений нет, их отсутствие фиксируют без искусственной row. Конфликт уже активного плана по тому же результату разбирают Architect и Owner (Architect/Owner triage). Само совпадение с открытой записью не мешает обычному плану (ordinary plan): prepare/finalize/backlink не являются его предусловиями. Настоящее продвижение записи требует штатного скрипта продвижения (promotion writer) и точного доказательства (exact proof). Перенос V2/K1 — отдельная работа после выпуска.

### Сверка руководства и трасса прохода

Перед init нового проекта прочитайте всё руководство и сопоставьте каждый применимый шаг с реализацией точки входа и её справкой: точная команда или ввод, предпосылки, ожидаемые stdout, stderr, код выхода и результат, действие при отказе. Для необязательных веток обновления и запроса в Planveyor укажите, применимы ли они, или причину пропуска. Теоретическая readiness не доказывает живой проход. Во время исполнения сохраните полный приватный trace всех вызовов, inputs, stdout/stderr, exit codes, результатов и повторов. Публичное описание создавайте только после исполнения и заменяйте в нём личные пути и учётные данные на `<REDACTED>`. Собственные трассы сессий агентного харнеса (native session traces) сохраняются отдельно. Скрипт извлечения трасс не заменяет полную трассу команд и не очищает её от личных данных.
