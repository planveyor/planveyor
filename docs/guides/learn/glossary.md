# Glossary

**English** · [Русский](glossary.ru.md)

The glossary explains the terms of the learning section and points to the chapter that tells more about each of them.

## Roles, names, and codes

| Term | What it means | Where to read more |
| --- | --- | --- |
| ACK | A mark in Planveyor with a link to the decision. For a request from a sibling, the `planveyor_upstream_request_ack` command sets it together with the `decided` status; for a rollout packet, ACK records that the packet was received. | [Exchanging changes with Planveyor](change-packets.md#upstream-request) |
| Architect | The role that decides what to do, what the scope of the task is, and how to accept the result. Architect writes the plan, answers the questions of other roles about the meaning of the task, and at the end accepts the work or returns it. | [Roles and task files](roles-artifacts.md#who-is-responsible-for-what) |
| CENSOR | The second pass of a role over its own files before the handoff: the role checks that everything discussed is written into the plan and the code draft, and adds what is missing. Architect does it before Planner, Planner before Coder, and Coder before Reviewer. | [Roles and task files](roles-artifacts.md#manager-and-the-handoff-check) |
| Coder | The role that writes the code and the tests from the code draft, runs the checks, and hands in the changed files together with their results. | [Roles and task files](roles-artifacts.md#who-is-responsible-for-what) |
| Codex home | The Codex settings directory: `PLANVEYOR_CODEX_HOME` or `~/.codex`. It holds `config.toml` with the model and the reasoning effort, the `[agents.*]` sections for the five role agents, and the role files. | [Launch](runtime-launch.md#where-things-are) |
| Copier | A project template tool. Planveyor uses it to lay out the contract in a new sibling and to update the contract on a move to a new version. | [Sibling: creation and upgrade](sibling-lifecycle.md#what-belongs-to-the-project-and-what-belongs-to-planveyor) |
| DACPAC | An SQL Server schema package that the database project builds. The harness of the SQL example publishes it to the dev database with the DacFx tool. | [Running example](sql-example.md#the-harness-and-the-live-run) |
| doctor | Check commands that do not start a model. `planveyor_entry_doctor` shows which Planveyor checkout and which project the facade selected, and `planveyor_consumer_doctor` compares the project contract with the engine version. | [Launch](runtime-launch.md#the-facade-and-project-selection), [Sibling: creation and upgrade](sibling-lifecycle.md#if-the-planveyor-checkout-has-moved-ahead) |
| F1–F62 | Items of the First-release backlog: each has a number, a priority, a responsible role, and a description of the work. A closed item records what exactly was closed. | [What works now and what comes next](capabilities-boundaries.md#limits-of-the-first-version) |
| `machine_authority_decision` | The decision of Architect in the `## Meta` block of the plan: whether the task introduces a new machine-readable record or format by which Planveyor scripts themselves admit, route, record, or close work. An ordinary task needs only the short form `not_applicable` with a reason; Owner confirms the full form. While the decision is missing, unconfirmed, rejected, or recorded twice, the plan linter and Oracle do not let the plan through to Planner. | [The plan and its statuses](plan-lifecycle.md#what-oracle-reads-and-reports) |
| Manager | The coordinator: by the plan status, it starts the role whose turn it is and checks what that role left. In one run, Manager takes at most 12 steps; after that, the same command is run again. | [Roles and task files](roles-artifacts.md#manager-and-the-handoff-check) |
| `MISSING-PATH` | A mark of the bundle check: a file of the bundle is missing on disk, and the check fails. | [The plan and its statuses](plan-lifecycle.md#the-bundle-and-its-two-checks) |
| Oracle | The `scripts/plan_status_oracle.py` script, which reads the plan status and the related files and reports what blocks the transition. Manager chooses the next role by its answer, and Owner sees the same answer in a short form through `planveyor sibling plan`. | [The plan and its statuses](plan-lifecycle.md#what-oracle-reads-and-reports) |
| Owner | A person, the owner of the project. Owner sets the goal, answers the questions that only a person decides, authorizes the commit, and runs `git push` themselves. | [Roles and task files](roles-artifacts.md#who-is-responsible-for-what) |
| PI (process improvement) | A `### PI-NNN` record about a gap in the process: the symptom, the gap, the suggested fix, and the owner. The roles usually make the proposals during the docs closeout, the PI collector writes the record, and the records are kept in `docs/process_improvements/`. | [How Planveyor changes itself](self-development.md#process-improvements-pis) |
| `PLANNED` | A mark of the bundle preflight: the review file is recorded in the plan, but Reviewer has not created it yet. | [The plan and its statuses](plan-lifecycle.md#the-bundle-and-its-two-checks) |
| Planner | The role that writes the code draft: the exact list of target files, steps, and checks for Coder. | [Roles and task files](roles-artifacts.md#who-is-responsible-for-what) |
| `## Post-merge gate` | The plan section with a checklist for the time after the merge into the main branch. A plan in `Done` cannot keep open items in it, so if the task is closed before the merge, the whole section is replaced with an `N/A (why=…)` line that gives the reason. | [Task closeout](closeout.md) |
| Reviewer | The role that checks the result in two lanes: the risk lane looks for where it can break, and the contracts lane compares it with the plan. The conclusions of both lanes are combined into one review file. | [Review and acceptance](review-acceptance.md#two-reviewer-lanes) |
| `review-only` | A plan type that orders only a review, for example a review of a commit range. In it, the `Ready for Arch review` status means “the report is ready to be examined”, and S1 findings in the report are allowed. | [Review and acceptance](review-acceptance.md#architect-acceptance) |
| S1, S2, S3 | The severity scale of review findings. S1 Blocker returns the work for a fix, S2 Risk can be accepted deliberately, and S3 Nit concerns style, names, and small cleanup. | [Review and acceptance](review-acceptance.md#the-review-file) |
| Self-Planveyor | Work on the engine itself: the Planveyor root serves as the project, and the commands run without `--project`. | [How Planveyor changes itself](self-development.md#a-change-in-planveyor-itself) |
| `semantic_closeout_commit_pending` | A refusal reason of the closeout script: the plan is already in `Done`, its whole bundle is in the index, but there is no commit. If not the whole bundle is in the index, the reason is `semantic_closeout_has_unstaged_delta`; in both cases, run `planveyor sibling close`. | [Task closeout](closeout.md#a-plan-in-done-without-a-commit) |
| Sibling | A separate Git repository of your project, created from Planveyor. It holds the product code, the stack harness, the plans, the reviews, and the local role rules. | [Sibling: creation and upgrade](sibling-lifecycle.md) |
| SID | The id of an agent harness session. It is stored in the `.planveyor.session.<key>` pointer, and the wrapper uses it to continue the same role session. | [Launch](runtime-launch.md#session-and-sid) |
| tSQLt | A unit test library for SQL Server. A test in it is a stored procedure, the tests of one class live in a separate schema, and a `tSQLt.FakeTable` call replaces a table with an empty copy for the duration of the test. | [Running example](sql-example.md#data-and-tests) |
| ZCode | An agent harness with its own Manager route, which works only in the Planveyor root. In a sibling, ZCode is suitable for a chat with the `/planveyor-plan-draft` skill. | [Launch](runtime-launch.md#zcode) |

## Concepts

| Term | What it means | Where to read more |
| --- | --- | --- |
| Acceptance (Arch review) | The decision of Architect on the plan and the review file: accept the work, return it for a fix, or replace the plan with a new one. When the roles run through the `planveyor sibling` commands, the acceptance is the first non-empty line `Вердикт: принято.` (verdict: accepted) in the `## Архитектурное ревью` section (or `## Arch review`) of the review file. | [Review and acceptance](review-acceptance.md#architect-acceptance) |
| Agent harness | The program in which a role session runs: Codex CLI, Claude Code, or ZCode. By default, all roles work in Codex; Planner and Reviewer can be moved to Claude Code in a single-role launch and in the custom pipeline. | [Launch](runtime-launch.md#agent-harness-codex-or-claude-code) |
| Analysis (`analysis_wave`) | The contour in which the roles answer a narrow question from the repository files and compare options. The result of an analysis is a checked analysis pack and the decision of Architect about the next work. | [Development, analysis, and decomposition](work-contours.md#three-work-contours) |
| Analysis outcome | The decision of Architect at the acceptance of an analysis: development, decomposition, an Owner question, defer, or reject. It is recorded in the `## Promoted route artifact` section of the plan. | [Development, analysis, and decomposition](work-contours.md#five-analysis-outcomes) |
| Analysis pack (`## Analysis pack`) | The result of an analysis: the sources read, the options, the assumptions, and the recommendation. On the move to `Planner finalize`, Planner moves it from the plan to a separate file in `docs/analysis_packs/`. | [Development, analysis, and decomposition](work-contours.md#how-the-roles-work) |
| Backup | The earlier project directory, which the upgrade renames to `.<name>-before-<first 12 characters of the new commit>`. It holds the whole project, including `.env.local`; delete it yourself when the upgrade plan is accepted. | [Sibling: creation and upgrade](sibling-lifecycle.md#where-the-risk-remains) |
| Bundle check (`planveyor_plan_bundle`) | The script that collects the exact bundle of the plan and checks that all its files are in place. Planner runs the preflight (`--preflight`) before `Ready for Coder`; before the diff, Reviewer checks only the composition and the integrity of the bundle (`--scope-check`); Reviewer and Architect run the final check (`--check`) after the review. | [The plan and its statuses](plan-lifecycle.md#the-bundle-and-its-two-checks) |
| Child plan | A plan for one part of a large goal in a decomposition. Coder creates it from the template with the `Ready for Planner` status, and then the plan goes through its usual cycle. | [Development, analysis, and decomposition](work-contours.md#how-the-roles-work) |
| Code draft | The Planner file with the list of target files and the steps for Coder. It lies in `docs/code_drafts/` under the plan name with the `__code_draft.md` ending. | [Roles and task files](roles-artifacts.md#task-files) |
| Code draft traps | The `## Critical invariants / traps / bypass paths` section of the code draft: the cases where a check turns green without proving anything, and what closes each such case. | [Running example](sql-example.md#what-the-plan-and-the-code-draft-say) |
| Code snapshot (`examples/sql/`) | Files of the unpublished SQL project from commit `f4f707b`, attached to the section: the procedure, its tests, the adaptation smoke test, the test run script, and the harness are copied unchanged, and an excerpt with two tests is taken from the harness tests. | [Running example](sql-example.md#code-snapshot-in-examplessql) |
| Codex agent (`agent_type`) | A role agent inside the Manager session in collab mode. Manager creates it with a `spawn_agent` call by one of the five types that the `[agents.<type>]` sections in `config.toml` describe, and gives it the next work with a `followup_task` call. | [Launch](runtime-launch.md#manager-collab) |
| Collab mode (Manager collab) | The mode in which Manager works as the main Codex session and starts the roles as its agents. In a sibling, it is opened by the Manager window `planveyor sibling tui` (TUI mode) and by the one-shot turn `planveyor sibling run` (manual console mode). | [Launch](runtime-launch.md#manager-collab) |
| Commit policy (`COMMIT_POLICY`) | A line in the header of the role assignment that says who makes the commit. With `human_explicit` (manual console mode: `planveyor sibling architect` or `run`), Owner makes the commit with `planveyor sibling close --commit`; with `native_existing` (TUI mode and any other launch), Architect makes it itself. | [Review and acceptance](review-acceptance.md#who-makes-the-commit) |
| Contract | Written rules, formats, and boundaries of responsibility. The consumer contract consists of the role definitions, prompts, playbooks, templates, ADRs, and skills that the project got from Planveyor through Copier. | [Sibling: creation and upgrade](sibling-lifecycle.md#what-belongs-to-the-project-and-what-belongs-to-planveyor) |
| Contract notice | A JSON file in `docs/contract_notices/` of Planveyor: what changed in the contract or the engine, and what the project should do and check. On a sibling upgrade, its actions and checks go into the upgrade plan. | [Exchanging changes with Planveyor](change-packets.md#contract-notice-what-a-new-version-brings) |
| Contract test | An engine test that reads a document or a prompt and checks that the required markers and rules are in place. | [Engine tests](engine-tests.md#a-contract-test) |
| Contracts lane | The second Reviewer lane (`reviewer_code_contracts`). The task plan serves as its contract: the lane compares the result with it, then combines both lanes into the review file and sets the overall status. | [Review and acceptance](review-acceptance.md#two-reviewer-lanes) |
| Current plan | The plan that the `planveyor sibling` commands work with. You select it with `planveyor sibling plan` and the file path, and the path is stored in `.planveyor.planpath`. | [The plan and its statuses](plan-lifecycle.md#the-plan-file) |
| Custom pipeline | The mode in which Manager calls the roles one by one through their wrappers, each in its own session. It is chosen, for example, so that Planner or Reviewer work in Claude Code. | [Launch](runtime-launch.md#manager-custom-pipeline) |
| Decomposition (`decomposition_wave`) | The contour in which the roles split an accepted large goal into child plans with an execution order. The result of a decomposition is an umbrella plan, child plans, and follow-ups. | [Development, analysis, and decomposition](work-contours.md#three-work-contours) |
| Development (`developer_wave`) | The default contour: the result and the scope of the task are clear, and the output is the changed files, the check results, the review, and the commit. | [Development, analysis, and decomposition](work-contours.md#three-work-contours) |
| Direct order check | A separate call of the procedure in the SQL example: the `run-tests.sql` script inserts products with IDs 30, 10, 20, and the harness requires them to come back in the order 10, 20, 30. The order is checked this way because the table comparison in tSQLt sees only the set of rows. | [Running example](sql-example.md#data-and-tests) |
| Docs closeout | The step after the task commit: in TUI mode, the same roles do it in the Manager window; in manual console mode, the next `planveyor sibling run` starts it. Usually four roles in two stages, `general` and `followups`, move into the shared project documents what is worth keeping, write process improvements, and propose follow-ups. If the documents need a commit, Architect makes it in TUI mode, and Owner authorizes it separately in manual console mode. | [Task closeout](closeout.md#docs-closeout) |
| Documentation linter (`planveyor_doc_lint`) | The check of Planveyor documents: broken relative links, file paths in backticks, and required shared phrases in groups of related documents. | [Engine tests](engine-tests.md#documentation-linter) |
| Engine | Shared Planveyor mechanisms: commands, role launch, and lifecycle checks. | [Launch](runtime-launch.md#where-things-are) |
| Engine tests | The tests of Planveyor itself, on Python `unittest`, in the `scripts/test_*.py` files. The `make test-scripts` target finds them all with one discovery. | [Engine tests](engine-tests.md#how-the-suite-is-built) |
| Evidence | Check results tied to a version of the files; in the plan, they are written to the `## Evidence` evidence log. After a file is edited, a new check is needed. | [Tests and evidence](testing-evidence.md#evidence-is-tied-to-a-version-of-the-files) |
| Evidence log (`## Evidence`) | The plan section to the end of which the roles append what they ran and with what result. An acceptance criteria item is marked `[x]` only by an entry in the log or by a file with the result. | [The plan and its statuses](plan-lifecycle.md#the-evidence-log-and-questions) |
| Exact bundle | All task paths that are checked together: the target and deleted files, the plan, the code draft, the review, and its assets. The task commit gets the changed files of this bundle, and only them. | [The plan and its statuses](plan-lifecycle.md#the-bundle-and-its-two-checks) |
| Facade (`bin/planveyor`) | The shared entry point to all engine commands. The facade finds the Planveyor checkout and the project, and runs the command in a separate clean `zsh -df` process. | [Launch](runtime-launch.md#the-facade-and-project-selection) |
| First-release backlog | The `docs/release_backlog.md` list with the open and closed items F1–F62, one item without a number, and four process improvements: PI1–PI3 and a separate source-bound PI. The items have no deadlines. | [What works now and what comes next](capabilities-boundaries.md#where-development-is-heading) |
| Follow-up | Work that was decided to be done later, with a responsible party and a reason. The roles propose such tasks during the docs closeout, and the `followups_apply.py` script writes them to `docs/followups/` (in `plan.v2` plans). | [Task closeout](closeout.md#docs-closeout) |
| Handoff digest | The script that collects into one answer the state of the plan, the code draft, and the review, together with the answers of Oracle and the bundle check. It only reads files itself. | [Engine tests](engine-tests.md#a-helper-script-test) |
| Harness | The project scripts that build it, deploy it to the dev environment, and run the stack tests. In the SQL example, these are the `sql.py` script and the `make` targets from `setup` to `db-proof`. | [Running example](sql-example.md#the-harness-and-the-live-run) |
| Integrity checks (`planveyor_verify`) | Checks of the tracked Planveyor files for tokens, keys, email and server addresses, private paths, references to Python from Homebrew, and traces of a failed automatic replacement. With `--full`, a run of all engine tests is added. | [Engine tests](engine-tests.md#integrity-checks) |
| Live run | A run of the stack checks on a real dev environment, for example `make db-proof` on the dedicated dev database of the SQL example. Owner decides in the stack brief who does it: the roles or a person. | [Running example](sql-example.md#the-harness-and-the-live-run) |
| Local sections | Two sections with fixed headings, `## Локальные правила стека` (local stack rules) and `## Разрешённое локальное переопределение процесса` (allowed local process override), in eight prompts and playbooks of a sibling. Their text belongs to the project, and a Planveyor upgrade carries it over unchanged. | [Sibling: creation and upgrade](sibling-lifecycle.md#local-sections) |
| Manual console mode | Work on a plan in a sibling with separate `planveyor sibling …` commands: each one finishes and exits, and Owner makes the commits with `close --commit` after the preview. After each commit, the next command starts a new Manager and new roles. | [Stack sibling guide](../stack-sibling.md#two-ways-to-work-on-a-plan) |
| Merge tracker | The local file `.planveyor.merge_tracker.md` with the order of the post-merge check steps; it is not committed. By the tracker, Manager continues the check from the step where it stopped. | [Post-merge check](postmerge.md#steps) |
| Offline tests | Tests that feed the code prepared inputs instead of a real database or service. In the SQL example, these are the 40 harness tests: they check how the harness parses substituted SQL Server answers and when it refuses. | [Tests and evidence](testing-evidence.md#kinds-of-checks) |
| Operator | A person or an agent with access to the dev database who, in the SQL example, did the live runs and started the roles. Planveyor has no such role. | [Roles and task files](roles-artifacts.md#how-it-went-the-getreordercandidates-task) |
| Phase prompt | The instruction of a role for the current plan status, for example `architect_status_driven.md`. In a sibling, the role reads the copy of the prompt from the project itself. | [Launch](runtime-launch.md#phase-prompt-and-commit-policy) |
| PI collector | The `process_improvements_collect.py` script. During the docs closeout, it adds a record for each proposal of the roles to the process improvements file of the plan and rebuilds the `index.md`, `deferred.md`, and `promotion_surface.md` summaries. | [How Planveyor changes itself](self-development.md#process-improvements-pis) |
| PI promotion | The step at which a PI record is linked to an already existing execution, usually a plan, and gets the `promoted` status. The promotion script does not create the plan itself. | [How Planveyor changes itself](self-development.md#process-improvements-pis) |
| PI reconciliation | The step at which the `process_improvements_reconcile.py --apply` script (it is run separately) sets `handled` on the PI records whose execution plan is already in `Done`. | [How Planveyor changes itself](self-development.md#process-improvements-pis) |
| PI triage | The step at which Architect assigns a PI record a target file, a repository, and a delivery mode, and Owner changes the `P?` priority to `P0`, `P1`, or `P2`. After the triage, the record gets the `triaged`, `deferred`, or `rejected` status. | [How Planveyor changes itself](self-development.md#process-improvements-pis) |
| Plan | The task file in `docs/plans/` with the goal, the scope of the task, the decisions, the questions, and the evidence log. The status in its header shows whose turn it is now. | [The plan and its statuses](plan-lifecycle.md) |
| Plan linter (`planveyor_plan_lint`) | The `scripts/plan_lint.py` script, which checks the form of the plan and the code draft and names what is missing. With the `--as-status Done` flag, it checks the plan as if the status were already `Done`. | [The plan and its statuses](plan-lifecycle.md#how-it-went-the-getreordercandidates-plan) |
| Plan queue | The Manager mode that runs several related plans in a row (`planveyor_q_set`, `planveyor_manager_collab_tui --q`). The queue has no end-to-end check, and work on it is deferred; `planveyor sibling run` runs one selected plan. | [What works now and what comes next](capabilities-boundaries.md#limits-of-the-first-version) |
| Plan status | The `**Status:**` line in the plan header: it shows whose turn it is now. A status like `Ready for …` hands the work to the next role, and `Done` means that the work is accepted and committed. | [The plan and its statuses](plan-lifecycle.md#statuses-and-who-sets-them) |
| Playbook | A document with the detailed work procedure of a role, for example for a commit review or a decomposition. Playbooks lie in `docs/playbooks/`; they come to a sibling with the contract. | [How Planveyor changes itself](self-development.md#what-changes-and-where-it-lives) |
| Post-merge audit | The report of Architect at the `post_merge_audit` step of the post-merge check: in it, the requirements of the merged plans are compared with the code, the checks, the documents, and the range review. | [Post-merge check](postmerge.md#steps) |
| Post-merge check | The check of a commit range `BASE..HEAD` that is already merged into the main branch: the range review, the plan harvest, the audit, the archive, and the local commit. Manager runs it in merge mode, and out of the box it works only in Planveyor itself. | [Post-merge check](postmerge.md) |
| Q&A log (`## Q&A log`) | The plan section with the questions of the roles: the number, whom the question is for, whether it blocks the work, and whether Owner is needed. Usually the role that asked a question closes it with a `status=closed` line, and the `planveyor sibling answer` command closes an Owner question. | [The plan and its statuses](plan-lifecycle.md#the-evidence-log-and-questions) |
| Range review | The review of all `BASE..HEAD` commits at the `review_range` step of the post-merge check. `planveyor_review_range_init` creates a `review-only` plan for it, and Reviewer writes the report in two lanes from the `_template_merge_range.md` template. | [Post-merge check](postmerge.md#range-review) |
| Receipt | A record of a completed action and its result. For example, the operator receipt `operator-validation.md` holds the command, the time, the exit code, the file checksums, and the output of the live run. | [Tests and evidence](testing-evidence.md#evidence-is-tied-to-a-version-of-the-files) |
| Review | The file with the conclusions of the two Reviewer lanes and the verdict of Architect, one per task. It lies in `docs/code_reviews/` or, if all target files are in `docs/`, in `docs/doc_reviews/`; the review assets are kept in `docs/code_reviews/assets/`. | [Review and acceptance](review-acceptance.md#the-review-file) |
| Risk lane | The first Reviewer lane (`reviewer_code_risk`): it looks for where the result can break. It writes its conclusion to the evidence log of the plan and puts the details in a separate file in the review assets. | [Review and acceptance](review-acceptance.md#two-reviewer-lanes) |
| Risk selector | The `review_artifact_lint.py --select-risk-lane` script, which Manager calls between the Reviewer lanes. It answers `selected`, `missing`, or `blocked`, and the contracts lane starts only on `selected`. | [Review and acceptance](review-acceptance.md#two-reviewer-lanes) |
| Role definition | The description of what a role is responsible for and where its boundaries are; role definitions lie in `docs/roles/`. Together with the phase prompt and the wrapper, it defines the role. | [Roles and task files](roles-artifacts.md#role-prompt-and-wrapper) |
| Rollout (rollout packet) | A packet with a change that Planveyor issues for one specific repository; the recipient adopts it with its own plan. A sibling does not receive such packets yet: changes come to it through an upgrade with a contract notice. | [Exchanging changes with Planveyor](change-packets.md#rollout) |
| Runner | The agent harness selected for a role: `codex` or `claude`. The choice is stored in `.planveyor.runner.<role>` and read by the role wrapper. | [Launch](runtime-launch.md#agent-harness-codex-or-claude-code) |
| Runtime | The Planveyor checkout from which the commands run. It holds `bin/planveyor`, the scripts, the shared rules, and the prompts. | [Launch](runtime-launch.md#where-things-are) |
| Session key | The name of a role session in the `.planveyor.session.<key>` pointer. There are seven keys: `architect`, `planner`, `coder`, `reviewer`, `reviewer_code_risk`, `reviewer_code_contracts`, and `manager`. | [Launch](runtime-launch.md#session-and-sid) |
| Sibling template (`copier_template/`) | The Planveyor directory with the files that a new sibling gets. The copies of documents and skills in it match the originals byte for byte, and a test checks this. | [How Planveyor changes itself](self-development.md#what-changes-and-where-it-lives) |
| Skill | A set of instructions for an agent harness that is called by name in a chat: for example, `$planveyor-plan-draft` creates a task plan. In a sibling, the skills come with the contract and lie in `.agents/skills/`. | [The plan and its statuses](plan-lifecycle.md#the-plan-file) |
| Stack adaptation plan | The first plan of a new sibling; its scope includes the stack harness, the root `README.md` of the project, and the local role rules. The adaptation is finished when the plan is committed and the documents are closed. | [Sibling: creation and upgrade](sibling-lifecycle.md#the-first-plan-stack-adaptation) |
| Stack brief | The `stack_brief.md` file in `docs/` of the project with the decisions about the stack, the dev environment, the commands, and who runs the live checks. The skill creates the stack brief together with the adaptation plan, and Architect asks Owner questions about the empty fields. | [Sibling: creation and upgrade](sibling-lifecycle.md#the-first-plan-stack-adaptation) |
| Structural checks | The plan linter, Oracle, and the bundle check. They confirm that the plan, the code draft, and the review are filled in by the rules, that the status allows the transition, and that the files are in place; the tests and the live run check how the code works. | [Tests and evidence](testing-evidence.md#kinds-of-checks) |
| Target files (targets) | The files that the task changes or on which its check relies. Planner keeps their list in the code draft, in the `code_draft_meta.targets` field. | [The plan and its statuses](plan-lifecycle.md#the-bundle-and-its-two-checks) |
| Target snapshot (`bundle_sha256`) | The checksum of the content of all target files in the `**Target:**` line of the review. | TUI mode | The main path of work on a plan in a sibling: one Manager window for the whole plan, from the draft to the end of the docs closeout.
