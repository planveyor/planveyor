# Sibling под свой стек

Sibling — отдельный Git-репозиторий для вашего кода, планов и правил стека. Движок Planveyor остаётся во внешнем checkout. Эта инструкция ведёт от создания проекта до первой полезной задачи, а затем применяется к каждой следующей задаче.

Основные команды — `planveyor sibling …`. Они определяют проект по текущему каталогу, берут выбранный план и проверяют действующую версию движка. Вы выбираете задачу, отвечаете на вопросы ролей и подтверждаете коммиты.

## Один раз: среда и создание проекта

Первая версия поддерживает macOS. Нужны Git, zsh, rg, подготовленное окружение с Python 3.12, Copier 9.18.2 и PyYAML по `requirements-dev.lock`. Для работы ролей нужен авторизованный Codex CLI с пятью настроенными ролями: см. [настройку Codex](launch-and-role-modes.md#настройка-codex). Инструменты и dev-среда вашего стека готовятся отдельно. Отсутствующую предпосылку команда назовёт; устанавливать или настраивать её автоматически Planveyor не будет.

В подготовленном терминале откройте каталог выбранного checkout Planveyor без незакоммиченных изменений. Init и upgrade проверяют это сами; отдельная Git-команда не нужна. Если `planveyor` уже доступен в `PATH`, следующий шаг пропустите. Иначе сделайте команду доступной в этой вкладке:

```sh
export PATH="$PWD/bin:$PATH"
```

Эта строка использует текущий checkout и не меняет shell config. В новой вкладке нужен тот же выбранный checkout в `PATH`. Прямой вызов из его корня — `./bin/planveyor`; отдельный установщик команд не требуется.

Выберите каталог нового проекта. В примере это `~/my-stack`; заменяется только имя вашего проекта:

```sh
planveyor sibling init ~/my-stack
cd ~/my-stack
```

Родитель каталога должен существовать. Каталог находится вне checkout Planveyor; путь проходит через обычные каталоги без символических ссылок. Имя начинается с латинской буквы или цифры и содержит только буквы, цифры, `.`, `_`, `-`; имя `default` недопустимо. Существующий непустой проект команда сохраняет и отказывает в init.

Init получает версию выбранного движка сам, делает первый коммит от вашей Git identity и закрепляет её для следующих коммитов этого sibling. Если имя и email ещё не настроены, задайте вашу пару явно:

```sh
planveyor sibling init ~/my-stack --author-name "Your Name" --author-email "you@example.invalid"
```

После успешного создания команда проверяет контракт и сообщает результат. Init ещё не создаёт план и заполненную анкету.

## Адаптация под ваш стек

Откройте sibling в обычном чате Codex или ZCode. Скиллы уже находятся в `.agents/skills/`; отдельно устанавливать их не нужно. Codex использует `$planveyor-plan-draft`, ZCode — `/planveyor-plan-draft`.

Передайте в чате:

```text
$planveyor-plan-draft Создай и сделай текущим план адаптации sibling под мой стек по docs/_template_stack_brief.md. Создай docs/stack_brief.md как вход плана. Задай вопросы по неподтверждённым решениям. Следующую полезную задачу согласуем отдельно.
```

Добавьте известные вам факты о языке, хранилище, тестах и dev-среде. Скилл создаёт план и анкету, а Scope плана включает обвязку стека, корневой `README.md` проекта и локальные правила ролей. Код из Scope затем реализует Coder.

Скилл использует выбранный trusted facade из окружения запуска. Если приложение не видит команду `planveyor` и ему не передан `PLANVEYOR_RUNTIME_ROOT`, оно попросит выбрать checkout движка один раз. Путь не надо записывать в публичные планы или правила стека.

Начните обсуждение с Architect:

```sh
planveyor sibling architect
```

Прочитайте вопрос и предложенные варианты. Чтобы передать свой ответ:

```sh
planveyor sibling answer
planveyor sibling architect
```

При нескольких вопросах команда покажет их id. Например, ответ на показанный вопрос `Q2`:

```sh
planveyor sibling answer Q2
```

Ответ вводится обычным текстом; формат журнала и время команда оформляет сама. Пустой ввод и отмена не подтверждают предложенный вариант. Повторяйте обсуждение, пока Architect не согласует необходимые решения и не попросит подтвердить раздел «Как я понял задачу». Подтверждайте его после чтения; дополнительные полномочия роли и условия приёмки требуют вашего явного решения. Ответы по умолчанию на частые вопросы собраны в разделе [«Типовые вопросы Architect»](#типовые-вопросы-architect).

Проверить выбранную задачу и следующий шаг можно в любой момент:

```sh
planveyor sibling plan
```

Если скилл создал план без выбора, попросите его сделать этот фактический план текущим. Для самостоятельного переключения используйте `planveyor sibling plan` с путём существующего плана, который вы выбрали. Команда не выбирает задачу по последней дате файла.

## Типовые вопросы Architect

Architect спрашивает, когда в анкете или плане не хватает решения, и обычно сразу предлагает ответ. Ниже ответы по умолчанию на частые вопросы адаптации и обычной задачи. Они написаны для любого стека: подставьте в ответ факты своего стека из анкеты и поручения.

Проход может вести агент по вашему поручению. Тогда он отвечает по этой таблице и пишет в ответе, что отвечает по поручению Owner. Решения, уже принятые в анкете и плане, он не пересматривает и не согласует заново. Остальные вопросы он возвращает вам: список под таблицей.

| Вопрос | Ответ по умолчанию | Что подставить |
|---|---|---|
| Подтвердить раздел «Как я понял задачу» | Перечитать актуальный текст. Подтвердить, если он совпадает с анкетой и поручением и не добавляет работы сверх Scope. Иначе назвать расхождение и попросить исправить. В адаптации следующая полезная задача остаётся отдельным поручением. | Назначение проекта и проверку готовности его среды |
| Поле анкеты с предложенным ответом | Принять, если предложение выполняет условие «Достаточно, если» из этого раздела шаблона анкеты. Иначе дополнить до этого условия. | Факты своего стека |
| Версии инструментов | Взять версии, которые уже установлены и закреплены в файлах проекта. Новые версии не выбирать. Отсутствующий инструмент назвать как предпосылку. | Инструменты и файлы, где закреплены версии |
| Какое окружение использовать для команд проекта | Уже подготовленное окружение через `PATH` текущего процесса; фактическую версию проверяет обвязка стека. Системные инструменты не устанавливать: зависимости проекта ставит только согласованный в анкете `make setup`, их кэши лежат в `.tmp/`. Не менять shell config, HOME и конфиг Codex. Личные пути не писать в план, README и правила. | Интерпретатор или SDK вашей среды |
| Как убедиться, что запись идёт в dev-среду | Код проверяет согласованный маркер назначенной dev-среды до каждой записи. Нет маркера — отказ без записи. Новое значение маркера не вводить. Сервер, маркер и учётные записи роли не меняют. | Маркер и способ его проверки в вашем хранилище |
| Где параметры подключения | `.env.local` с правами 0600, в `.gitignore`, не отслеживается Git. В план и README попадают только имена ключей. | Имена ключей |
| Какие команды допустимы | Цели стека из анкеты. У каждой указано, нужна ли сеть или живая цель, кто её запускает, ожидаемый код выхода и отчёт. | Цели `make` вашего стека |
| Кто запускает живые цели | Роли в песочнице с сетью, если сеть у выбранного Codex home уже настроена. Иначе оператор-человек. Сеть агент сам не включает. | Цели и роли, которые их запускают |
| Условия приёмки | Принять, если каждое условие называет свой тест и проверяет результат, входы и выходы, которые требует поручение. Недостающий отрицательный или граничный случай добавить. Новых требований сверх поручения не вводить. | Тесты вашего фреймворка |
| Чем доказать результат | Отчётом текущего прогона на ревьюируемых байтах. Reviewer повторяет проверку сам, а при варианте «только оператор» её по запросу Reviewer повторяет оператор. Старый зелёный результат и отчёт другой задачи не переносятся. | Формат и место отчёта тестов |
| Найдена открытая запись follow-up по той же теме | Сослаться на неё в Context links плана и оставить запись без изменений. Её продвижение не условие обычной задачи. | Ссылку `source_ref#item_id` |
| Что вне объёма | Production, бизнес-данные, конфигурация сервера, CI и другие ОС, если поручение не говорит иначе. | Исключения вашего проекта |

Агент возвращает вам вопрос, если он касается:

- значений секретов (агент может только проверить права файла);
- production, бизнес-данных или цели без маркера dev-среды;
- прав администратора, изменения сервера, маркера или учётных записей;
- расширения Scope сверх поручения и анкеты, смены стека или версий;
- включения сети, изменения конфигурации Codex, HOME или выбранного движка;
- публикации: remote, push, issue, видимость репозитория;
- коммита, на который нет вашего прямого разрешения в этой сессии;
- решения, которого нет ни в анкете, ни в поручении, ни в этой таблице.

Ответ из таблицы не заменяет проверок. Красный результат возвращает работу роли. Подтверждение раздела «Как я понял задачу» не разрешает коммит.

## Провести план

Когда intake Architect завершён, запустите обычный Manager:

```sh
planveyor sibling run
```

Manager ведёт существующие роли Architect, Planner, Coder и Reviewer по статусу плана. Команда подготавливает необходимые сессии; вручную запоминать их id или обновлять после коммита не нужно.

Если Manager ждёт вашего решения, выполните `planveyor sibling answer`, затем повторите `planveyor sibling run`. Если достигнут лимит хода, повторите тот же `run`. Ошибка проверки возвращает работу соответствующей роли; её нельзя заменить согласием с предыдущим зелёным результатом.

При адаптации роли создают обвязку стека, его проверки и правила. Правила находятся в двух локальных секциях восьми файлов; обновление сохраняет именно эти секции:

| Роль или фаза | Файл |
|---|---|
| Architect | `docs/tools/prompts/architect_status_driven.md` |
| Planner | `docs/tools/prompts/planner_status_driven.md` |
| Coder | `docs/tools/prompts/coder_status_driven.md` |
| Coder: миграции | `docs/tools/prompts/coder_migrations_gate.md` |
| Reviewer | `docs/tools/prompts/reviewer_status_driven.md` |
| Ревью коммита | `docs/playbooks/review_staged_or_commit.md` |
| Ревью диапазона | `docs/playbooks/review_merge_range.md` |
| Post-merge audit | `docs/playbooks/post_merge_audit.md` |

Для стека с credentials локальный `README.md` назовёт имена ключей и защищённый файл. Введите значения в локальном редакторе; в чат, планы и отчёты секреты не передаются. Для `.env.local` нужны права 0600, игнорирование Git и отсутствие отслеживания. Файл читает обвязка, а роли вызывают только принятые команды стека. Администратор готовит dev-среду с нужными маркерами и правами; обвязка должна проверять её до записи.

Если ролям нужен доступ к dev-среде, согласуйте один вариант в анкете: сеть у выбранного Codex home или выполнение живых команд человеком. Настройку сети и её область действия описывает [руководство запуска](launch-and-role-modes.md). Planveyor сам не открывает сеть и не меняет Codex home. При operator-only варианте роль остановится с конкретной командой; после её запуска передайте фактический результат через `answer`. Красный результат требует исправления и повторной проверки.

## Коммит и закрытие документов

Когда Architect принял итоговое ревью и Manager предлагает закрытие, сначала посмотрите подготовку:

```sh
planveyor sibling close
```

Этот вызов показывает состояние и будущий набор; статус, index и сессии не меняет. Открытый вопрос или обязательная проверка остановит подготовку и даст следующий шаг. Прочитайте показанный набор и сообщение, проверьте его изменения в редакторе. Если после просмотра правили файлы, повторите preview. Только после этого разрешите конкретный коммит:

```sh
planveyor sibling close --commit
```

Флаг `--commit` — ваше явное подтверждение выполнить проверенный текущий набор; дополнительный общий «yes» не нужен. Команда повторно проверяет готовность, переводит принятый план в `Done` и коммитит только его точный набор. Чужие staged файлы, неготовое или устаревшее ревью и ошибки текущих проверок означают отказ. Роли не получают скрытого разрешения на коммит.

После коммита плана команда предложит отдельный ход Manager для закрытия документов:

```sh
planveyor sibling run
planveyor sibling close
```

Просмотрите подготовленный хвост документов. Если требуется его отдельный коммит, выполните `planveyor sibling close --commit`: это ваше отдельное подтверждение уже показанного набора. Первый `--commit` не запускает роли и не подтверждает ещё не созданные документы. После коммита документов команда сразу проверяет закрытие; при оставшемся обязательстве повторите указанный шаг.

Законченной работа считается после сообщения о завершённом закрытии документов. Один статус `Done`, первый коммит или успешный doctor ещё не означает, что весь шаг завершён. При нескольких циклах закрытия команда попросит уточнить фактический цикл; она не выбирает произвольный каталог. Отдельный post-merge audit может оставаться открытым, если так предусмотрено планом.

## Следующая задача и готовность

После завершения адаптации передайте в том же чате:

```text
$planveyor-plan-draft Создай и сделай текущим обычный план по моему прямому поручению: <результат и наблюдаемая проверка>. Покажи matching open follow-up, сохрани его неизменным и добавь source_ref#item_id в Context links.
```

Опишите желаемый результат. Адаптация согласует назначение и готовность стека; следующая полезная задача — отдельное прямое поручение Owner. Реальные findings адаптации проходят штатный capture; zero findings допустимы.

Скилл выполняет bounded discovery. Matching row остаётся unchanged: `status=open`, `plan=null`, `disposition_kind=null`, `disposition_ref=null`, `disposition_commit_oid=null`; literal `source_ref#item_id` — только контекст плана. Automatic backlink запрещён. Если совпадений нет, фиксируется отсутствие совпадений без искусственной row. Конфликт уже активного плана по тому же результату требует Architect/Owner triage. Само совпадение открытой row не мешает ordinary plan: prepare/finalize/backlink не являются его предусловиями. Настоящее продвижение row требует штатного promotion writer и exact proof; V2/K1 port — отдельная post-release работа.

Повторите `architect` → ответы → `run` → `close` → отдельный `close --commit`, затем docs `run` → `close` → при показанном обязательстве отдельный `close --commit` → `ready`. Перед следующей задачей завершите закрытие документов текущей. Эта последовательность описывает ожидаемые шаги, а не уже выполненный passage.

До fresh init прочитайте весь runbook и сопоставьте каждый применимый шаг с существующей entrypoint/help реализацией: literal command/input, prerequisites, ожидаемые stdout/stderr/exit code/result и действие при отказе. Для optional upgrade/upstream branches укажите применимость или причину пропуска. Теоретическая readiness не доказывает живой проход. Во время исполнения сохраните полный приватный trace всех вызовов, inputs, stdout/stderr, exit codes, результатов и повторов; публичное описание создавайте только после исполнения, заменяя private paths/credentials на `<REDACTED>`. Native session traces сохраняются отдельно; trace extractor не является полным command trace или sanitizer.

Проверить текущее обязательство:

```sh
planveyor sibling ready
```

Команда проверяет контракт, состояние выбранного плана и закрытие его документов. Живые проверки вашего стека Coder и Reviewer выполняют по принятой анкете и плану; `ready` их не запускает заново. Сверьте фактические результаты приёмки: старый отчёт или отчёт другой задачи их не заменяет. Результат не означает публикацию, выполнение отдельного post-merge audit или разрешение писать в production.

Для большой задачи остаются обычные [analysis](../playbooks/analysis_wave.md) и [decomposition](../playbooks/decomposition_wave.md) маршруты. Попросите draft skill выбрать соответствующий тип плана с Architect. Отдельные низкоуровневые entrypoints и queue описаны в [режимах запуска](launch-and-role-modes.md); `sibling run` работает с выбранным планом и сам очередь не создаёт.

## Получить новую версию Planveyor

Sibling закрепляет конкретную версию движка: роли, шаблоны и проверки работают по одним правилам, и результат можно воспроизвести. Команды получают эту версию и технические идентификаторы сами. Новый checkout движка сначала выбираете вы; обновление sibling проходит отдельным обычным планом.

Обновите установленный checkout Planveyor своим обычным способом. Команда `sibling upgrade` не делает скрытый pull или переключение Git branch. Выбранная версия должна продолжать прежнюю историю и быть доступна на ветке или теге. Проведите и закройте текущую работу, сохраните изменения, завершите активные сессии и выйдите из каталога sibling: upgrade меняет каталоги местами.

Из внешнего каталога выберите ваш проект:

```sh
planveyor --project ~/my-stack sibling upgrade
```

При успешном обновлении команда сама получает новую версию, проверяет сохранность локальных правил и печатает пути backup и плана адаптации. Извещения включаются в этот план, но отдельно команда их не выводит. Она создаёт и выбирает план адаптации обновления. Откройте sibling заново и проведите этот план тем же циклом `architect` → `run` → `close`. Сообщение об обновлённом контракте ещё не означает принятую адаптацию.

Если обновление остановилось с candidate, исходный sibling остаётся на месте, backup и план обновления ещё не созданы. Текущая обёртка возвращает код 3 и скрывает stdout с путём candidate и списком проблем; сообщения stderr остаются видимыми. Кандидат находится рядом с проектом в `.<имя>-upgrade-<12 знаков нового коммита>`. Повторный запуск той же команды назовёт точный путь сообщением `candidate path already exists: …`.

Откройте candidate в обычном чате ИИ-клиента. Попросите разобрать его фактический `git status`, файлы `.rej`, маркеры `<<<<<<<` и изменения локальных секций, проверить точный diff и сохранить принятый результат в candidate. После его реального review и коммита примите candidate из внешнего каталога:

```sh
planveyor --project ~/my-stack sibling upgrade --accept-candidate
```

Выбранная версия движка должна оставаться той же. Потеря локальных секций, неоднозначное переименование, битое извещение или занятый путь backup требуют отдельного разбора. Команда их не исправляет обходным способом. Backup содержит полную копию проекта, включая credentials и локальное состояние; сохраняйте его приватно и удаляйте сами после принятия адаптации.

## Предложить изменение Planveyor

Правила вашего стека меняются в sibling. Общую проблему движка или процесса передают в Planveyor через upstream request. Это второй публичный сценарий обмена: предложение из sibling, решение в source и возвращение исправления обновлением.

В обычном чате sibling попросите подготовить request по `docs/upstream_packets/_template.md`: симптом, пробел процесса, предлагаемое исправление и ссылки на вашу задачу и место обнаружения. Факты вашего стека вынесите в `Target-Specific Facts To Filter`; секреты, адреса серверов и абсолютные пути в request не входят. Подготовка request проходит проверку и ваш review; просьба подготовить файл ещё не разрешает отправку.

После принятия и коммита request отдельно разрешите отправку issue. Для этого используется установленный и авторизованный GitHub CLI `gh`, обычная команда `gh issue create --body-file` с точным подготовленным файлом. Попросите агента показать готовую команду и публичное тело; не надо переносить текст вручную или подставлять технические id. Если `gh` не настроен, отправка останавливается с понятной предпосылкой. Создание issue само по себе не означает, что предложение принято.

Сопровождающий Planveyor принимает request штатными source-local `planveyor_upstream_request_import` и `planveyor_upstream_request_ack`: они работают только в physical source root, а из sibling их не запускают. Решение и исправление проходят обычный source plan. Изменение контракта или поведения сопровождается извещением в `docs/contract_notices/` с проверками и действиями для sibling.

После публикации выбранной версии выполните `sibling upgrade`. Созданный план адаптации включает извещение и обновление локальной копии request. Роли проверяют результат по вашему стеку; завершите оба коммита и закрытие документов. Формат пакетов и низкоуровневые readbacks описаны в [Lifecycle и пакеты](lifecycle-and-packets.md).

### Пример: SQL Server sibling → исправление provenance → обновление

Это условный обмен после публикации версии, а не отчёт об уже отправленном issue. Допустим, в `planveyor-mssql` provenance плана теряет id текущего чата при вызове facade. SQL Server и tSQLt объясняют место обнаружения; передача контекста чата — общая механика Planveyor.

Попросите подготовить request по шаблону с фактическими ссылками на план и review вашего sibling. Для примера содержание такое:

| Поле request | Содержание |
|---|---|
| `origin_repo` | `planveyor-mssql` |
| `requested_source_canon_path` | `bin/planveyor` |
| `symptom` | В provenance нет id текущего чата после вызова facade. |
| `process_gap` | Child facade теряет контекст вызывающего чата. |
| `suggested_fix` | Передавать id как provenance-only вход и проверить unset, empty и present. |
| `Target-Specific Facts To Filter` | MSSQL/tSQLt остаются локальным стеком и не становятся умолчаниями движка. |

Проведите подготовку и review request, затем отдельно разрешите отправку issue через `gh issue create --body-file`. Сопровождающий source импортирует request, принимает решение и проводит обычный план исправления. Извещение по [существующему формату](../contract_notices/README.md) включает проверку provenance через facade и consumer doctor; действия sibling — проверить собственные SQL-правила и обновить локальную копию request. Source-only ACK фиксирует реальные decision/execution refs и состояние `decided` в source; сам ACK sibling не обновляет.

После публикации выберите новую версию Planveyor и выполните `sibling upgrade`. В плане адаптации Coder проверит provenance и реальные проверки вашего SQL-стека, а также согласует поля и refs локального request с извещением. Это target-local изменение проходит review, два точных коммита и docs closeout; source-only ACK из sibling не вызывается. При blocked candidate сначала разбирается его реальная причина. Issue, source `decided` и успешный Copier не заменяют принятие адаптации.

## Если команда остановилась

| Что сообщает команда | Следующий шаг |
|---|---|
| Нет инструмента, подходящего Python или авторизации | Подготовить названную предпосылку и повторить ту же команду. |
| Не выбраны проект или план | Открыть нужный sibling и поручить скиллу выбрать созданный план; несколько задач выбираете вы. |
| Открыт вопрос Owner | `planveyor sibling answer`, затем `architect` или `run`, которые попросили решение. |
| Достигнут лимит Manager | Повторить `planveyor sibling run`. |
| Ревью или доказательство устарело | Вернуться к указанной роли; старый зелёный результат не подтверждает новые изменения. |
| В index есть чужие файлы | Разобрать их отдельно; `close` не очищает и не коммитит чужую работу. |
| Требуется коммит | Просмотреть `close`, затем явно выполнить и подтвердить `close --commit`. |
| Документы ещё не закрыты | Выполнить указанный ход Manager/закрытие; следующую задачу начинать после завершения. |
| Версия runtime расходится с sibling | Выбрать соответствующий движок или провести план обновления. |
| Upgrade сохранил candidate или backup | При коде 3 найти candidate и разобрать его фактические проблемы по шагам выше; после успеха проверить план адаптации и сохранить backup до его принятия. Original не заменять вручную. |

Справка доступна обычной командой `planveyor sibling --help`. Она не запускает роли и не изменяет проект.
