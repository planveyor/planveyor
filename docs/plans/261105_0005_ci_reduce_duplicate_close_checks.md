## Problem
1. В большом методе s02 каждая из четырёх ролей повторяет одну пару проверок закрытия в ветвях False и True. Текущий source подтверждает: пара выполняется до различающей ветви коррекции и до reserve; обе ветви в этот момент проверяют один `retryable` outcome.
2. В опубликованном run 41832023322 тест завершился успешно, а job позднее исчерпал предел. Восемь повторных команд заняли в том запуске 820.297 с. Это переданный исторический замер, а не текущий runtime/hosted proof и не прогноз точного ускорения.

## Как я понял задачу
Убрать повтор пары в True только в одном уже выбранном методе; сами команды и assertions пары остаются в False до reserve.
Сохранить восемь отдельных consumer roots, обе ветви коррекции, отрицательные проверки и полный успешный сценарий Reviewer.
Следующий contour — обычный bounded dev-plan: Architect формализовал смысловой контракт; Planner финализирует executable inventory/proof commands и code draft, Coder владеет реализацией.
Новых решений Owner и изменений принятого объёма нет; первичный intake и отдельный CENSOR завершены, дальнейший handoff не требует повторного разрешения на уже выбранное изменение.
Перед staging для коммита, Done, semantic commit или closeout обязателен отдельный Root checkpoint по точному unstaged candidate; публикация остаётся отдельной командой.

## Solution (high level)
1. Architect и Planner проверяют границу повторяемой пары, сохраняемые assertions и exact target.
2. Coder ограничивает существующую пару `sibling close` / `sibling close --commit` ветвью `second_malformed=False` до reserve. Сами команды и assertions пары остаются.
3. Owning роли квалифицируют адресный результат и manifest exact-once. После Planner/Coder/dual review/Architect checks Architect отдаёт Root точный unstaged candidate: base HEAD/tree, полный exact member list, byte count/content SHA-256, Git/Unix modes, helper bundle identity и proof refs. Root проверяет приватные имена на независимой копии и возвращает scoped decision. До этого решения запрещены любые staging для коммита, Done, semantic commit и closeout. После разрешённого конечного коммита применяется существующий p0.
