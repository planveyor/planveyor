## Problem
1. Ошибка формата general PI сейчас останавливает collector без штатного ограниченного повторного хода той же роли.
2. Общий `collector_error` не доказывает eligibility. Повтор должен иметь точную типизацию, текущую identity и устойчивый бюджет.
3. Подсказки `close`/`run` после отказа должны отражать blocked/retryable outcome без ложного успеха или петли при rc=0.

## Как я понял задачу
Реализовать одну дополнительную автоматическую коррекцию malformed PI на роль в текущем cycle через существующие native механизмы.
Initial dispatch не расходует бюджет; reservation сохраняется durably до повторного dispatch и не сбрасывается crash/reentry.
Исправленный полный ответ пишет та же persistent роль, Manager передаёт его collector побайтно.
Второй malformed ответ и повторный вход с уже зарезервированной попыткой приводят к bounded stop; старый untyped отказ не получает автоматический допуск.
Owner уже разрешил этот ordinary developer_wave и минимальные изменения existing native carrier/helper/writer; технический checkpoint принят, новых Owner-решений не требуется.
Architect формализовал accepted contract; Planner связывает его с exact code draft, derived tagged MAD ref и native executable preflight. Нового Owner GO для этого handoff не требуется.

## Solution (high level)
1. Collector типизирует только отказ формата; admission и reservation принадлежат existing capture helper, итоговый permission возвращает existing docs-closeout readback.
2. Одна CAS-protected reservation внутри текущей aggregate receipt сохраняет исходный отказ и расходует дополнительную попытку до сообщения той же persistent роли.
3. Manager выполняет только helper-admitted correction output того же plan/cycle/role, без повторных docs edits и без изменения bytes; после успеха продолжается исходный general order и штатный checkpoint/followups.
4. Sibling run/close читают тот же helper outcome и сохраняют обратную совместимость rc, но больше не обещают успешный close и не направляют blocked в бесконечную петлю.

Новый controller, registry, helper file или общий retry framework не создаются. Exact executable code draft и детализация реализации принадлежат Planner/Coder.

### General PI format correction contract

Поля и action ниже — новые bounded additions в перечисленных existing файлах, а не claim об уже существующей реализации.

- Collector `error_type=pi_format_error` появляется только для dedicated format exception строгого `Process improvements` parser: unsupported prose/field, missing structural fields, mixed no-op, неверный canonical section/структура. Это subtype существующего ValueError contract. Нельзя классифицировать по тексту error или blanket ValueError/Exception. Source/role/cycle mismatch, invalid UTF-8, authority/I/O/object drift и unknown errors не получают этот type. `capture_state=blocked`, existing reason/error, raw-byte input digest и object maps сохраняются; parser не ослабляется.
- Fresh `begin` добавляет `general_pi_format_corrections={}` в existing aggregate receipt. Для correction отсутствие этого carrier, malformed/unknown keys, legacy untyped leaf и stale binding — fail-closed, без backfill. Обычный historical green/read-only lane не становится correction admission и не переписывается.
- Read-only `general_pi_format_correction_admission` в schema-validated `docs_closeout_payload.v1` имеет schema `general_pi_format_correction_admission.v1`, `state=not_applicable|retryable|blocked`, reason, exact plan/cycle/role, `attempts_reserved`, `max_extra_attempts=1`, `next_dispatch` и helper-owned proof. `retryable` — только permission запросить reservation, ещё не permission отправить сообщение. Current blocked capture сохраняется как blocked даже при retryable admission.
- Полный predicate: exact current project/source semantic identity и current native authority; active same cycle; canonical ordered general prefix Architect → Coder → Planner → Reviewer полностью green и contiguous от aggregate baseline; ровно одна текущая typed blocked leaf с before=after и empty path delta; все subsequent roles отсутствуют; нет general checkpoint/followups progress/failure checkpoint/final objects. Проверяются реальные receipt/object identities и hashes, current live PI map, derived freshness, foreign dirty PI, protected docs delta и current plan/review/source proof. Недоказанное отсутствие, invalid prefix/suffix/effect/identity/drift/host/phase = blocked до mutation.
- Existing `scripts/followups_capture.py` получает bounded action `reserve-general-pi-correction`. Он повторно выводит admission, проверяет retained proof/CAS revision и effect context и атомарно публикует ровно одну запись роли `general_pi_format_correction.v1` внутри `general_pi_format_corrections`. Запись связывает project/source/cycle/role, helper-generated reservation id, `attempts_reserved=1`, исходный canonical receipt path/object/content identity, полный `original_receipt_utf8` и его SHA-256. Встроенный original сохраняет точные receipt bytes после replacement leaf; original raw input digest/error остаются доказуемыми. Отдельный файл счётчика/registry не появляется.
- Транспорт reservation: будущий candidate action `followups_capture.py reserve-general-pi-correction --project-root <root> --plan-ref <plan_ref> --capture-cycle-id <UUIDv4> --role <Role> --docs-closeout-json -` получает полный retained schema-green docs-closeout JSON через stdin, без восстановления proof со стороны Manager или caller receipt path. Перед публикацией writer самостоятельно повторно выводит полный predicate. Только fresh CAS publication возвращает `state=reserved` как transition result с exact reservation identity; top-level aggregate `state=started` и остальные role slots сохраняются. Повторный reserve не возвращает разрешающий reserved outcome. Этот action в frozen runtime не исполняется; его реализует Coder внутри existing helper.
- Только успешный fresh transition reservation даёт invocation-local permission на один dispatch. Повтор reserve, потерянный result, crash до/после dispatch и новый Manager invocation не дают нового permission: durable spent=1 возвращает blocked с причиной consumed reservation, без redispatch. Crash после committed reservation до сообщения тоже расходует попытку и ведёт к Owner stop; идемпотентный ack не разрешает второй send. Initial dispatch не пишет reservation и не расходует бюджет.
- Correction пишет та же persistent роль через существующий handle. Canonical correction message содержит ROLE, PLAN_PATH, PRE_STATUS_LINE, exact cycle, исходную причину, тот же general PROMPT_FILE и полный перечитанный general prompt, запрет любых повторных docs/file edits и требование полного output с `## Process improvements`. Manager не собирает ответ за роль, не вырезает prose, не заменяет содержательный PI no-op и передаёт raw corrected bytes в тот же collector/source/cycle.
- Existing collector выполняет допустимый blocked → continuation replacement только после revalidation новой reservation для typed correction lane, с сохранением original и счётчика. Generic existing legacy/private primitive не превращается в automatic retry authority. Второй malformed ответ сохраняет новый refusal и spent reservation, останавливает family без checkpoint/followups/stage/commit; третьего автоматического dispatch нет. После corrected green новая fresh same-cycle readback закрывает именно эту mutation, а не success text.
- Проверка перед reservation и допуск corrected ingest имеют разные observer boundaries: spent readback запрещает новый reservation/send, но не отменяет единственный уже допущенный corrected output в той же invocation. Collector повторно проверяет stored reservation и её original blocked leaf/source/role/cycle/object binding, а не требует снова state=retryable и не резервирует ещё одну попытку. Stale/replaced binding, второй refusal либо потеря original invocation permission ведут к bounded stop; direct legacy/private replacement не является route для автоматического повторного dispatch.
- Каждая следующая general роль имеет свой независимый budget slot; green prefix не redispatch-ится. После четвёртой green leaf остаются штатные checkpoint и четыре followups records. Их schemas, sole writer, ordinary V2 compact bind/freeze и terminal capture-aware proof не обходятся.
- `sibling close` при blocked/retryable не stage-ит и не commit-ит; `run`/post-run plan readback не советует close как успешный следующий шаг. Retryable message указывает единственную correction в текущем живом Manager/handle; blocked/consumed/unknown требует Owner stop. Новый CMD invocation не изображает сохранённый TUI handle и не выполняет автоматический redispatch/rebinding. `scripts/planveyor.zsh` остаётся contextual: уже существующий post-run `plan` readback использует исправленный Python consumer, dispatch adapter и commit policy не меняются.
- Существующий explicit continuation вход — `planveyor_manager_collab_cmd run <explicit PLAN_PATH> --followups-capture-cycle-id <UUIDv4>`; выбранный TUI сохраняет текущие persistent handles. Wrapper в `scripts/planveyor/role_runtime.zsh` уже передаёт PLAN_PATH и отдельный FOLLOWUPS_CAPTURE_CYCLE_ID, не склеивает selector с MANAGER_CMD. А2 меняет только native Manager consumer/admission перед generic incomplete/bootstrap stop; новый wrapper/entrypoint и автоматический init не нужны. Missing/malformed selector, cached plan inference, другой project/source/cycle и утраченный handle не открывают correction. Owner-facing help/readback в этом slice — PI README, Manager source/copy и existing sibling blocked/retryable output; отдельные руководства остаются у назначенного автора.
