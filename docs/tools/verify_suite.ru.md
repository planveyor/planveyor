# Руководство Owner: маршруты проверки

[English](verify_suite.md) · **Русский**

`planveyor_verify` — сводная проверка установленного корпуса Planveyor. Она запускает его зарегистрированные модули проверки целостности и ничего не меняет. По умолчанию идёт быстрый маршрут проверки целостности, а `--full` добавляет один канонический прогон тестов через `unittest discover`. Реализацию и точный набор модулей задаёт установленная копия Planveyor, а это руководство описывает контракт для оператора.

## Запуск

Запускайте команды из физического корня Planveyor через публичный фасад:

```zsh
./bin/planveyor planveyor_verify
./bin/planveyor planveyor_verify --format json
./bin/planveyor planveyor_verify --module <module-name>
./bin/planveyor planveyor_verify --full
make verify
make verify-full
make test-scripts
```

Маршрут по умолчанию выполняет зарегистрированные проверки целостности, кроме тестов `unittest`. Он не запускает ни `unittest discover`, ни прежний дублирующий прогон тестов переносимости внутри модуля. `--full` добавляет ровно один канонический прогон, и его нельзя сочетать с `--module`. `make verify` идёт маршрутом по умолчанию, `make verify-full` передаёт `--full`, а `make test-scripts` остаётся отдельной командой канонического прогона. Для одного заявления о полной проверке выберите что-то одно: `make verify-full` или `make test-scripts`. Не запускайте их вместе.

## Границы платформы и CI

Первый выпуск поддерживает работу на macOS с подготовленным окружением Python 3.12 и зависимостями из `requirements-dev.lock`. Ещё должны быть доступны Git, zsh и ripgrep. Загрузчик идентичности исходников (source identity) технически принимает Python 3.10–3.12, но поддержку первого выпуска это не расширяет. Профили CI на macOS и обязательная итоговая проверка описаны ниже; сама настройка результатом hosted CI не считается. Нативная проверка на Windows и Linux не завершена.

Имена модулей, запущенных установленной версией, есть в JSON-отчёте
`planveyor_verify --format json`; передайте нужное имя через `--module`. Для работы с проектом выберите его явно через фасад, перед командой, если модуль рассчитан на проверку дерева проекта.

## Проверка совместимости в CI

Состав выборки `compat310` задаёт точный список ID в `scripts/test_shards.json`: тесты потока загрузчика и обработки отказов, выбора интерпретатора, разбора идентичности исходников и настоящего пути init, doctor и upgrade через публичный фасад и Copier. Это ограниченная проверка совместимости. Она не заменяет полный набор на Python 3.10 и не расширяет поддерживаемую среду первого выпуска. Целевая версия Python для mypy остаётся 3.10.

Команды запускаются из физической копии репозитория выбранным подготовленным интерпретатором:

```zsh
"$PYBIN" -B scripts/run_test_shard.py --matrix
"$PYBIN" -B scripts/run_test_shard.py --check
"$PYBIN" -B scripts/run_test_shard.py --subset compat310 --report <fresh-report-path>
```

`--matrix` читает структуру матрицы, не импортируя тесты. `--check` импортирует тесты через каноническое обнаружение и проверяет все ID настроенных выборок и полное разбиение: каждый тест должен стоять ровно в одной части. Тела тестов при этом не выполняются. Запуск выборки сначала повторяет эти проверки, а затем отбирает нужные тесты из исходных в каноническом порядке и сохраняет хуки уровня модуля и класса. Неизвестные, пустые, повторные или отсутствующие ID и неверное полное разбиение приводят к отказу. Каталог отчёта должен существовать, а файлов отчёта и событий по указанным путям ещё не должно быть. `--subset` нельзя совмещать с выбором полной части или локального профиля.

Отчёт и парный файл `.events.jsonl` связывают упорядоченный список ID, хеш манифеста, сведения об интерпретаторе Python, HEAD и учёт запущенных и завершённых тестов. В отчёте выборки стоят `selected_subset=compat310` и `selected_shards=[]`, в отчёте полного или локального запуска — ID его частей и `selected_subset=null`. Если учёт неполный, запуск прерван или HEAD после исполнения отличается от HEAD до него, результат не будет зелёным. Локальный результат проверки совместимости не доказывает ни успеха в hosted CI, ни покрытия полного набора на Python 3.10 и не обещает, сколько времени займёт проверка после push. Полные маршруты проверки, описанные выше, остаются отдельными.

## Профили CI и обязательная итоговая проверка

Workflow в репозитории выбирает профиль по событию. Push в `main` и `pull_request` запускают быстрый профиль `fast`: части `core` (`--subset fast`), `contracts-a` и `contracts-b` на Python 3.12 и отдельную часть `compat310` на Python 3.10. Ежедневный запуск по `schedule` (`17 2 * * *` UTC) и ручной запуск через `workflow_dispatch` выбирают полный профиль `full`: все 14 частей на Python 3.12 и `compat310` на Python 3.10. Правки только в документации проверку не обходят. Шага выпуска в workflow нет. Профили CI не меняют поведения `--matrix` без профиля, локальных профилей и полных маршрутов проверки, описанных выше.

Прежде чем отобрать тесты, CI импортирует их через каноническое обнаружение и проверяет полное разбиение: каждый тест должен стоять ровно в одной части. Затем CI сверяет состав частей с эталоном, который не зависит от списков ID выборок в манифесте: эти списки можно менять. В часть `core` входят 16 заранее заданных тестов-свидетелей безопасности, каждый — тестовый метод целиком. В `contracts-a` входят все найденные тесты модуля `test_planveyor_plan_bundle`, в `contracts-b` — все тесты 29 модулей из явного списка в `scripts/run_test_shard.py`. Эти три части не пересекаются. Девять заранее заданных ID выборки `compat310` сверяются отдельно. С новыми тестами в этих модулях части `contracts-a` и `contracts-b` растут, и прежние снимки их размеров — не верхний предел.

Задача `shard-matrix` перед импортом тестов устанавливает объявленные в проекте зависимости и отдельным шагом проверяет состав частей, независимо от отбора тестов. Четыре проверки метаданных выполняются один раз за прогон: строгая проверка документации и переводов, линтер изменённых планов, проверка типов с целевой версией Python 3.10 и сканирование публичного содержимого. В `fast` за них отвечает часть `contracts-b`, в `full` — `s01`. В PR база для линтера изменённых планов — только merge-base с целевой веткой, без запасного варианта: если его не удаётся вычислить, шаг падает. Для push база — коммит `before` из события, если он задан и есть в истории, иначе — корневой коммит; для `schedule` и `workflow_dispatch` — `HEAD^1`, иначе — тоже корневой. Событие, выбранная база и HEAD записываются в журнал.

Запуск части в строгом режиме требует флагов `--ci-strict`, `--ci-profile`, `--ci-part`, `--ci-python`, `--ci-event`, `--ci-run-id`, `--ci-run-attempt` и `--ci-expected-sha`. Если профиль и отбор тестов (`--shard` или `--subset`) заданы без `--ci-strict` и контекста CI, скрипт завершается с ошибкой ещё до выполнения тестов. Для PR нужен ещё `--ci-pr-head-sha`; при других событиях этот флаг передавать нельзя, запуск завершится с ошибкой. Ожидаемым считается коммит из доверенного `github.sha`; для PR это merge-коммит, который GitHub создаёт для проверки PR, а head SHA передаётся отдельно. Недостаточно, чтобы HEAD до и после выполнения совпали между собой: оба должны равняться ожидаемому коммиту.

Посмотреть и проверить профили можно в подготовленной копии репозитория; тесты при этом только импортируются и не выполняются:

```zsh
"$PYBIN" -B scripts/run_test_shard.py --matrix --ci-profile fast
"$PYBIN" -B scripts/run_test_shard.py --check --ci-profile full
```

В строгом режиме отчёт получает дополнительные проверяемые поля `ci_profile,ci_part,ci_event,ci_run_id,ci_run_attempt,ci_expected_sha,ci_pr_head_sha,ci_expected_python,ci_python`. Фактическая версия Python (старший и младший номер), манифест, ожидаемый SHA, отбор и непустые упорядоченные списки запланированных, запущенных и завершённых ID должны совпасть с ожиданием для этой части, которое скрипт вычисляет сам, не из отчёта. Результат строгого запуска зелёный, только если учёт полный, нет проваленных тестов, ошибок, пропусков (skip) и прерывания, а исходники не менялись во время запуска. Локальных запусков запрет на пропуски не касается. На Python 3.12 отчёт хранит длительности тестов, которые записывает сам unittest, на Python 3.10 — только общее время, а поле длительностей равно `null`. Замеры времени нужны только для диагностики.

Для отчётов workflow использует стандартные actions артефактов, закреплённые по полному SHA. В артефакте `planveyor-ci-<run>-<attempt>-<part>` лежит только `result.json`. Шаг выгрузки отчёта выполняется с `if: always()`, то есть и после упавших тестов, а если отчёта нет, это ошибка. Обязательная итоговая проверка **`ci-summary`** тоже выполняется с `if: always()` и зависит от задач `shard-matrix` и `verify`. Она сама запускает скрипт с `--ci-summary DIRECTORY --ci-profile fast|full` и передаёт ему из доверенного контекста GitHub событие, ID прогона, номер попытки и SHA, а также `--ci-needs-json JSON`. Читаются отчёты только текущей попытки. Части `ci-summary` не перезапускает и ожидаемые ID не берёт ни из отчётов, ни из вывода задачи `shard-matrix`. В `full` части вместе должны покрыть все тесты канонического обнаружения, каждый ровно один раз; в `fast` — только тесты `core`, `contracts-a` и `contracts-b`. `compat310` в эту сверку не входит, её проверяют отдельно.

`ci-summary` падает, если:

- отчёта какой-то части или результата зависимости (needs) нет либо есть лишний;
- отчёт или данные needs повреждены или содержат повторяющийся ключ;
- отчёт относится к другой попытке или другому прогону, повторяется или учтён не полностью;
- часть или зависимость красная, отменена или пропущена.

Даже если матрица `verify` в целом зелёная, `ci-summary` заметит пропавший отчёт, часть `s02`, выполнившую тесты `s01`, два одинаковых, но неверных HEAD или красный отчёт части. Журнал событий (`.events.jsonl`) нужен только для диагностики: `ci-summary` не пересчитывает по нему результат и обходится без клиента API GitHub.

Поскольку `ci-summary` читает отчёты только текущей попытки, прогон повторяют целиком через «Re-run all jobs». Если в прошлой попытке хотя бы одна часть прошла, «Re-run failed jobs» её не повторит, отчёта этой части в новой попытке не будет, и `ci-summary` останется красной. Если перезапустить только `ci-summary`, она тоже будет красной. Для `full` это повтор всего профиля, сейчас около 2 ч.

В `fast` группа `concurrency` привязана к ref: новый прогон отменяет идущий. В `full` имя группы содержит ID прогона и номер попытки, поэтому новый полный прогон не вытесняет предыдущий, который ещё ждёт в очереди; свободных раннеров GitHub это не гарантирует. Обязательной проверкой (required check) `ci-summary` должны сделать настройки репозитория: сам workflow rulesets не меняет. Перед следующим выпуском нужен зелёный прогон `full` на том SHA, который выпускается. Локальные проверки на синтетических данных и настройка в исходниках не доказывают ни успеха в hosted CI, ни поведения очереди и отмены, ни публикации изменения и не гарантируют, что прогон уложится в час.

## Что значит результат

- `GREEN` / код выхода `0` значит, что прошли все обязательные зарегистрированные проверки. Даже тогда `WARN` может потребовать, чтобы оператор прочитал подробности и выполнил локальное предварительное условие, прежде чем считать работу готовой.
- `RED` / ненулевой код выхода значит, что хотя бы одна обязательная проверка не прошла. Прежде чем менять какой-либо артефакт, прочитайте названные модуль, метрику и подробности.
- Успешный прогон маршрута проверки подтверждает только те проверки, о которых он сообщает. Он не доказывает, что роли отработали, тесты целевого проекта прошли, ревью принято, пакет принят или задача закрыта по смыслу.

## Когда запускать

Запускайте нужный модуль после изменения его контракта, перед публичным выпуском или когда сомнение в переносимости или целостности нужно проверить узким чтением состояния. Пока разбираете блокер, берите самый маленький подходящий модуль. `--full` нужен, когда один сводный маршрут должен добавить канонический прогон, который охватывает несколько зарегистрированных границ.

## Если проверка предупреждает или падает

1. Прочитайте результат именно этого модуля и его подробности.
2. Определите, к чему относится замечание: к текущему содержимому репозитория, к внешнему выбранному проекту или к временному локальному состоянию.
3. Исправьте только названную причину, через тот жизненный цикл, которому она принадлежит.
4. Запустите тот же модуль снова. Если результат важен для передачи работы, запишите свежие доказательства.

Не ослабляйте проверку, не переписывайте посторонний артефакт и не глушите текущий отказ старым зелёным результатом.
