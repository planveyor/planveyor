# MCP и проверки целевого проекта

[English](mcp.md) · **Русский**

MCP, инструменты браузера и нативные инструменты дополняют объявленный контракт
проверок выбранного проекта. Они не создают универсальных правил для UI,
фреймворка или учётных данных.

## Выбор инструмента

1. Прочитайте `PLAN_PATH` и канон целевого проекта.
2. Выбирайте только инструмент или обвязку, которые там объявлены для текущих
   границ задачи.
3. Если линия UI или живого прогона не объявлена, запишите
   `N/A (why=not declared)`. Не подставляйте браузер, нативный вспомогательный
   инструмент, базу данных или команду фреймворка.
4. Запускайте функции Planveyor через публичный фасад:

~~~bash
./bin/planveyor planveyor_verify [--format json] [--full | --module …]
~~~

Без флагов это быстрый маршрут проверки целостности. `--full` добавляет один канонический прогон `unittest discover`, и его нельзя сочетать с `--module`; фасад передаёт `argv` без собственной ветки обработки.

Фасад проверяет копию Planveyor, из которой идут команды. Команда целевого
приложения, учётные данные и тестовые фикстуры принадлежат целевому проекту.

## Доказательства для UI

Для объявленной линии UI зафиксируйте:

- точный сценарий и предусловия;
- выбранный браузер или нативный вспомогательный инструмент;
- команду и её результат или читаемую квитанцию;
- полный набор визуальных артефактов;
- вердикт человека и решение по замечаниям.

Результат автоматизации и осмотр человеком независимы. Один снимок экрана не
доказывает весь контракт UI. Успешная команда тоже не закрывает визуальную
линию без объявленного вердикта.

## Ограничения среды

Если выбранной обвязке нужны браузер, сеть, устройство, локальный сервис или
запуск с повышенными правами, сначала получите честный результат настоящего
запуска. Недоступная среда — блокер или диагностика по контракту целевого
проекта. Не заменяйте её другим стеком и не выдумывайте учётные данные.

Не сохраняйте учётные данные, cookies, заголовки авторизации, идентификаторы
сессий, токены или личные пути в плане, квитанции, файле ревью или метаданных
снимков экрана. Используйте `<REDACTED>`.

## Границы MCP

Вывод инструмента MCP — вспомогательное доказательство, пока план или ревью
не укажет его роль в решении. Не принимайте доступность инструмента, текст из
чата или старый журнал за доказательство текущего поведения. Сохраняйте только
нужные публичные факты: выбранный инструмент, объявленные границы задачи в
целевом проекте, результат и устойчивую ссылку на артефакт.

## Закрытие

После линии UI или MCP:

1. Добавьте результат в ревью, которое ведёт роль, или в журнал проверок плана.
2. Повторите объявленную проверку для точного набора изменённых файлов.
3. Если изменились общие документы процесса, отдельно выполните применимые требования к доставке пакетами.
4. Если доказательств не хватает, остановитесь. Только ради того, чтобы закрыть
   линию доказательств, не меняйте целевой проект, не пишите в очередь, не делайте
   коммит или push.
