# Руководство Owner: сессии ролей Planveyor

[English](owner_runbook_codex.md) · **Русский**

Этот документ — публичное руководство по работе с копией Planveyor. Он описывает переносимый жизненный цикл. Учётные данные, тесты конкретного проекта и локальную автоматизацию он оставляет проектам, которые пользуются Planveyor.

## Публичная точка запуска

Planveyor запускается через фасад, который выполняет команды только в дочернем процессе. Не подключайте shell-скрипты реализации к родительской оболочке через `source`.

До первой публичной команды проверьте, что доступен `git`, Planveyor лежит в физической копии Git-репозитория и `HEAD` указывает на коммит. Фасад выполняет эту предварительную проверку до `--project` и до doctor. `planveyor_entry_doctor` не может восстановить или обойти среду Git, которая не прошла проверку.

Из физического корня Planveyor начните с этих команд:

```zsh
./bin/planveyor planveyor_entry_doctor
./bin/planveyor planveyor_runtime_info
./bin/planveyor planveyor_help
```

Эти команды только читают локальное состояние копии Planveyor и проекта. Готовность к запуску они не показывают: они не доказывают ни аутентификацию, ни доступность провайдера, ни допустимость плана, ни SID, ни вызов ролей через Manager, ни запуск роли.

Фасад находит свой корень по `bin/planveyor`. Чтобы загрузить идентичность исходников (source identity), нужен исполняемый файл Python 3.10–3.12, совместимый с Planveyor. Настроенный агентный харнес и его обычная внешняя аутентификация нужны живой команде, которая вызывает этот харнес. Codex и аутентификация Codex относятся только к путям через Codex. `planveyor_entry_doctor`, `planveyor_runtime_info` и `planveyor_help` их не проверяют. Прежде чем запускать роли или проверки, выберите совместимый Python 3.10–3.12 через доверенное окружение запуска. Фасад и вспомогательные скрипты используют именно его, а локальный файл проекта `.planveyor.pybin` исполняемый файл не выбирает. `bin/planveyor` запускает дочерний процесс через `env -i` и `zsh -df`, поэтому унаследованный `CODEX_HOME` и переменные окружения других инструментов в него не передаются. `PLANVEYOR_CODEX_HOME` допустим, только если оператор явно задаёт канонический внешний путь вне дерева файлов Planveyor. `HOME`, аутентификация, состояние клиента и `PLANVEYOR_STATE_ROOT` остаются внешними.

В корне выбранного проекта остаются локальные артефакты процесса: игнорируемые указатели `.planveyor.planpath` и `.planveyor.session.*`, записи режима collab `.planveyor.collab.*`, квитанции инициализации `.planveyor.init_runs/` и временный каталог `.tmp/`. Это не учётные данные и не внешний каталог настроек клиента, но при переносе или переписывании истории проекта их нужно сохранять отдельно.

## Явно выберите проект и работу

Вызов без `--project` работает с самим Planveyor. Для проекта, который пользуется Planveyor, передайте `--project` перед публичной командой и укажите абсолютный канонический путь к каталогу:

```zsh
./bin/planveyor --project /absolute/path/to/consumer \
  planveyor_plan_status_oracle --json docs/plans/YYYYMMDD_HHMM_topic.md
./bin/planveyor --project /absolute/path/to/consumer \
  planveyor_plan_set docs/plans/YYYYMMDD_HHMM_topic.md
./bin/planveyor --project /absolute/path/to/consumer \
  planveyor_planpath
```

Фасад меняет каталог только у чистого дочернего процесса и задаёт корень проекта только для этого вызова. Относительные пути разрешаются внутри выбранного проекта. Родительская оболочка не меняется, и каждый новый вызов снова требует префикса `--project`. При сопровождении самого Planveyor можно вызывать команды без префикса: `HOME`, аутентификация и состояние внешнего клиента, как и явно заданный `PLANVEYOR_CODEX_HOME`, остаются вне дерева файлов Planveyor, а игнорируемые указатели, записи collab и квитанции принадлежат корню выбранного проекта.

У запуска Planveyor один активный целевой проект и, для работы по плану, один явный путь к плану. Не выводите план из имени файла, прошлой сессии или упоминания в тексте. Сначала убедитесь, что существующий точный путь проходит Oracle, а затем сохраните указатель. `planveyor_planpath` доказывает только локальный выбор. Если указателя нет, команда предлагает `planveyor_plan_set <PLAN_PATH>`, но сам по себе указатель не доказывает готовность или допуск в жизненный цикл. Зелёная статическая проверка, старая квитанция или завершённая сессия роли сами по себе не доказывают, что текущие байты проходят следующую проверку жизненного цикла.

Прежде чем менять целевой проект, прочитайте его инструкции для участников и предпосылки. Тесты целевого проекта запускаются из его копии репозитория; Planveyor их не заменяет.

## Подготовка собственного проекта

Для нового проекта сначала создайте или выберите его копию репозитория средствами самого проекта. В документации проекта запишите инструкции для участников, подготовку среды выполнения, предпосылки по сервисам, команды тестов и проверок и владельцев учётных данных. Затем, ещё до запуска ролей и проверок, выберите в доверенном окружении запуска Python 3.10–3.12, совместимый с Planveyor. Абсолютный путь к проекту передавайте через `--project` перед публичной командой. Python выбирает окружение запуска; файл в sibling на этот выбор не влияет.

## Адаптация к стеку проекта

Planveyor сохраняет жизненный цикл, доказательства и правила передачи работы. Язык, фреймворк, локальные сервисы, миграции и собственные проверки целевого проекта определяет репозиторий проекта. До выполнения запишите эти предпосылки в план или документацию проекта, убедитесь, что доверенное окружение запуска даёт совместимый Python 3.10–3.12, и запускайте проверки целевого проекта из копии репозитория проекта. Не переносите в дерево файлов Planveyor локальную конфигурацию целевого проекта и учётные данные.

## Режимы ролей и Manager

Planveyor поддерживает отдельные сессии ролей и совместную работу под управлением Manager. Набор команд установленной версии показывает `planveyor_help`.

```zsh
./bin/planveyor planveyor_manager_init
./bin/planveyor planveyor_manager_collab_tui
./bin/planveyor planveyor_manager_custom_pipeline_tui --no-alt-screen
./bin/planveyor planveyor_manager_resume
```

Перед обычным TUI подготовьте по порядку: поддерживаемый интерпретатор, успешную проверку Oracle для существующего плана, указатель и SID Manager. Если SID нет, восстановление указывает на `planveyor_manager_init`. `planveyor_manager_collab_tui` без `--q` — живой путь для одного плана. После успешных проверок он передаёт `MANAGER_CMD=run`, а сам вызов роли остаётся условным результатом. `planveyor_manager_collab_cmd run <PLAN_PATH>` — альтернативный разовый живой путь. После TUI запускать его не обязательно.

Очередь — отдельный расширенный маршрут: после `planveyor_q_set <PLAN_PATH> --for-manager-mode manager-collab` используйте явную точку входа очереди:

```zsh
./bin/planveyor planveyor_manager_collab_tui --q
# либо
./bin/planveyor planveyor_manager_collab_cmd run Q
./bin/planveyor planveyor_manager_custom_pipeline_cmd run Q
```

Не создавайте псевдоним `--queue`.

Пошаговому режиму Manager (custom pipeline) нужны отдельные SID для Manager, Architect, Planner, Coder, `reviewer_code_risk` и `reviewer_code_contracts`: `planveyor_manager_init`, `planveyor_arch_init`, `planveyor_planner_init`, `planveyor_coder_init`, `planveyor_reviewer_code_risk_init`, `planveyor_reviewer_code_contracts_init`. Общий `planveyor_reviewer_init` не заменяет специализированные линии Reviewer. TUI пошагового режима — живой путь наблюдения и вызова ролей. Он не доказывает, что запустится каждая роль.

Чтобы возобновить отдельную роль, используйте её команду `*_resume` из `planveyor_help`. У выбранного режима два публичных входа: TUI и разовая команда `*_cmd`. Не повторяйте алгоритм конвейера самодельной цепочкой shell-команд.

Прямой маршрут Manager в ZCode описан в `docs/tools/prompts/zcode/manager_pipeline.md` (англ.). Это транспортная надстройка. Она не заменяет точки входа пошагового режима (Custom), режима native/collab, возобновления (resume), TUI и команд: все они сохраняются.

Обычный цикл роли:

1. Выберите проект и явный план.
2. Инициализируйте сессию роли или Manager, указанную в справке.
3. Передайте роли только задачу с чёткими границами, текущие доказательства и ожидаемый артефакт.
4. Прочитайте артефакт и направьте его объявленный статус следующей допустимой роли или проверке.
5. Создайте новую квитанцию, если изменились план, ревизия целевого проекта или намеченные границы задачи.

Owner выбирает режим работы и любой агентный харнес, который доступен установленной копии Planveyor. Manager может координировать выбранные роли, но не меняет молча агентный харнес, источник аутентификации, проект или план, которыми распоряжается Owner.

## Артефакты запусков инициализации

Для диагностики движок сохраняет локальное состояние запусков инициализации в выбранной копии репозитория. После привязки сессии `.planveyor.init_runs/by_sid/<SID>/` содержит `run.log` и `meta.json`. Для попытки до привязки SID те же файлы сохраняет `.planveyor.init_runs/pending/<role>/<run_id>/`. `.planveyor.session.<role>` — только указатель для подключения к сессии. Он не доказывает, что инициализация или запуск роли завершились успешно.

Эта запись запусков инициализации не охватывает `resume`, живой `tee`, раздельные `stdout/stderr` и перехват интерактивного TTY. Для них нужны отдельные текущие доказательства и подходящая проверка жизненного цикла.

## Передача работы с чёткими границами

Каждая передача работы должна называть:

- путь к плану и корень проекта;
- точные файлы или диапазон ревизий для ревью;
- ожидаемый артефакт на выходе;
- проверку, которая выбирает следующий шаг;
- одного допустимого следующего ответственного для случая, когда проверка проходит или блокирует работу.

После существенных изменений заново прочитайте статус. Текстовая сводка роли полезна как контекст, но долговечными записями передачи остаются план, ревью, вывод проверок и метаданные пакета.

## Жизненный цикл плана, ревью и закрытия

Planveyor сохраняет жизненный цикл, который начинается с плана:

1. Architect или Planner создаёт план с чёткими границами по шаблонам репозитория.
2. До выполнения план прогоняют через линтер плана и проверяют его статус.
3. Coder меняет только то, что разрешают границы задачи в целевом проекте, и сообщает результаты проверок.
4. Reviewer оценивает текущий диапазон и записывает замечания или доказательства для приёмки.
5. Нужную работу CENSOR или отложенную задачу закрывает явный план или принятое исключение.
6. Когда изменения слиты, целевой проект проходит проверки после слияния. Если нужно, создаются свежие записи документации, отложенных задач и пакетов.

Для исполняемого плана проверьте точный набор файлов перед последней передачей работы, если установленная копия Planveyor даёт такую проверку:

```zsh
./bin/planveyor --project /absolute/path/to/consumer \
  planveyor_plan_bundle --preflight docs/plans/YYYYMMDD_HHMM_topic.md
./bin/planveyor --project /absolute/path/to/consumer \
  planveyor_plan_bundle --check docs/plans/YYYYMMDD_HHMM_topic.md
```

`--preflight` проверяет предложенный набор файлов до ревью. `--check` оценивает готовый набор. Ни один из них не заменяет тесты целевого проекта, ревью текущего diff или обязательный артефакт приёмки по смыслу.

## Правила работы с очередью

Очередь Manager — это явный упорядоченный список путей к планам. Создайте или просмотрите её установленными командами очереди до того, как просить Manager её выполнить. Не вызывайте маркер очереди сам по себе, не используйте старую очередь после изменения плана и не считайте черновой файл источником истины об очереди.

Если план из очереди блокируется, остановитесь на указанной проверке. Исправьте или замените план, проверьте новый артефакт, затем осознанно обновите очередь.

## Диапазоны ревью и работа после слияния

Ревью и доказательства после слияния обязаны называть точный диапазон или ревизию, которые они покрывают. Запишите базовую и конечную ревизии (base и head) до того, как создавать ревью или пакет. Если диапазон изменился, повторите подходящие проверки.

Работа после слияния обычно включает:

- тесты целевого проекта и нужный прогон линтера документации;
- разбор ревью и отложенных задач с конкретным ответственным;
- привязку предложений по процессу, только если их доказательства актуальны;
- оформление пакета, если работа должна перейти между репозиториями.

Шаблоны репозитория в `docs/reviews/`, `docs/followups/` и `docs/process_improvements/` задают форматы долговечных записей. Сгенерированные сводки — производные представления. Пересобирайте их из текущих исходных артефактов и не правьте руками отметки времени или старые строки.

## Адресные пакеты

Адресный пакет передаёт работу с заданными границами из исходного репозитория в целевой. Это не профиль, не учётные данные и не механизм удалённого запуска.

Создавайте пакет, только когда известны исходный репозиторий, целевой репозиторий и нужный план. Разделяйте роли источника и цели: источник публикует запрос на принятие изменения, а цель записывает собственные локальные доказательства принятия и исход.

```zsh
./bin/planveyor planveyor_rollout_packet_create <target-repo> <topic-slug> \
  --source-plan docs/plans/<source>.md --target-kind plan_adoption
./bin/planveyor planveyor_rollout_packet_show docs/rollout_packets/<packet>.md
./bin/planveyor planveyor_rollout_packet_import_instructions \
  docs/rollout_packets/<packet>.md --print-target-plan-seed
```

Обычный порядок доставки такой: проект создаёт у себя план принятия (он же квитанция импорта), затем записывает один исход в выбранном проекте через публичный фасад:

```zsh
./bin/planveyor --project /absolute/path/to/consumer \
  planveyor_rollout_packet_outcome_set \
  --target-plan docs/plans/<target-adoption>.md --packet-id <id> \
  --packet-path docs/rollout_packets/<packet>.md --outcome <canonical-or-alias>
```

Эта команда меняет только локальную структурированную запись целевого проекта. Затем источник фиксирует отдельную квитанцию:

```zsh
./bin/planveyor planveyor_rollout_packet_ack \
  --packet docs/rollout_packets/<packet>.md --status imported \
  --target-plan docs/plans/<target-adoption>.md
```

ACK создаёт указатель на `docs/plans/<target-adoption>.md`, но сам по себе не доказывает готовый исход в целевом проекте. Пакет после ACK может остаться в ожидании исхода.

Текущее состояние записей смотрите командами `planveyor_rollout_packet_inbox`, `planveyor_rollout_packet_adoption_plan`, `planveyor_rollout_packet_query`, `planveyor_rollout_packet_reconcile` и `planveyor_rollout_packet_lint`. Пути пакетов держите локальными для источника, а в шаблонах используйте общие идентификаторы `<target-repo>`.

Для запросов в Planveyor используйте установленные команды `planveyor_upstream_request_show`, `planveyor_upstream_request_import`, `planveyor_upstream_request_ack` и `planveyor_upstream_request_query`. ACK записывает квитанцию и не утверждает, что целевой репозиторий выполнил слияние или принял изменение.

Проверка в режиме отчёта и повторного использования читает точный диапазон и не меняет пакет:

```zsh
./bin/planveyor planveyor_post_merge_packetization_gate --range BASE..HEAD
```

Чтобы восстановить конкретный локальный пакет источника или заново поставить на нём отметку, назовите его явно:

```zsh
./bin/planveyor planveyor_post_merge_packetization_gate_recover \
  --range BASE..HEAD --packet docs/rollout_packets/<packet>.md \
  --source-plan docs/plans/<source>.md --stage-packets
```

Для восстановления `--range` обязателен. `--source-plan` необязателен и указывает происхождение, а `--packet` при восстановлении можно повторять. Проверка без названного пакета работает в режиме отчёта и повторного использования и пакет не обновляет.

## Границы target-local

Planveyor поставляет публичные профили исходников `default` и `planveyor`. Профиль `target-local`, промпт роли для конкретного целевого проекта, учётные данные интеграции и политика проекта принадлежат репозиторию проекта. Если их там нет или их не удаётся прочитать, остановитесь с понятным блокером и не создавайте локальную замену.

Эта граница относится также к аутентификации, локальной настройке оболочки, настройке редактора, браузерам, доступу к базам данных и внешним сервисам. Держите их вне дерева файлов Planveyor и описывайте в репозитории проекта, когда они нужны для работы в целевом проекте.

## Устранение неполадок

1. Запустите `planveyor_entry_doctor` и `planveyor_runtime_info` из корня Planveyor.
2. Прочитайте в `planveyor_help` контракт установленных команд.
3. Проверьте, что выбранный проект, путь к плану, диапазон ревью и путь к пакету заданы явно.
4. Повторите самую узкую команду, которая только читает состояние и объясняет блокер: проверку статуса, линтер или Oracle.
5. Исправьте только названную предпосылку, затем создайте свежую квитанцию и только после этого продолжайте.

Если мешает блокер среды выполнения или авторизации, не копируйте учётные данные, не подключайте файлы реализации через `source`, не меняйте из дерева файлов Planveyor локальную конфигурацию целевого проекта и не повторяйте роль с другим скрытым контекстом.
