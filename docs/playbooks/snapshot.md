# Playbook: Snapshot (контекстный checkpoint)

Это **не роль**. Это повторяемый сценарий “сохранить/восстановить контекст” для новой сессии.

> Рекомендация по неймингу:
> - `TOPIC` = короткий slug в `snake_case` (англ.), например:
>   `integration_mismatch`, `workflow_state`.
>   - Если продолжаешь ту же тему в новой сессии — используй тот же `TOPIC` (чтобы легко находить последние snapshots).
>   - Если есть предыдущий snapshot по теме — укажи на него ссылку в блоке «Связанные артефакты» (цепочка восстановления).
> - `ROLE` = `architect|planner|coder|reviewer|owner` (кто делает snapshot).
>
> Триггеры “когда snapshot / когда plan”: `docs/plans/README.md`

# Задание: Снимок Понимания (Context Snapshot)
Проанализируй нашу беседу и создай **содержательный** Markdown-дамп для переноса в новую сессию. Snapshot — это «бэкап мозга»: цель — не экономить байты, а **сохранить смысл** (что решили, почему, какие варианты проверили, где риски/неясности).

Если решение было **неочевидным** — обязательно распиши **почему так сделали** (это экономит время сильнее любой краткости). Блоки, которые реально не относятся к теме, можно пропускать, но **не выкидывай историю/гипотезы**, если они влияют на дальнейшие решения. Нельзя додумывать или писать ради соответствия формату — отражаем только то, что обсуждали. Если чего-то не знаешь — помечай `UNCONFIRMED`. Если что-то не вписывается в структуру, упомяни это в разделе «Разное».

Ключевая граница:
- Snapshot = backup/handover/history artifact.
- Snapshot **не** является source of truth, effective spec или допустимым cited pointer'ом из active canon / audit-report / merge notes / follow-ups backlog.
- Если факт важен надолго, его нужно промоутить в plan / canon / review / audit / follow-up, а не ссылаться на snapshot.

Правила управляемости (без потери смысла):
- В начале snapshot обязательно заполни «0. Быстрый рестарт» (Goal/Now/Next/Commands/Working set).
- Tool-output/логи по умолчанию **маскируй**: `[MASKED: ...]` + команда/путь для воспроизведения. Суммаризацию делай только если без неё нельзя продолжать.
- PII/секреты: токены/ключи/пароли — только `<REDACTED>`; телефоны — только masked; внутренние `id` допускаются (если помогают отладке).
- Если в процессе нашли **регрессию/граблю/неочевидный контракт** — обязательно зафиксируй:
  - Repro (1–5 шагов) → Root cause → Fix → Regression test/Smoke → какие доки обновили (ссылками).
- Если snapshot потом будут читать как history/handover:
  - не замораживай transient repo-state (`dirty`, `untracked`, “локально создано ...”) как будто это долгоживущий факт;
  - либо зафиксируй exact live fact из `git status -sb` / `git log -1 --oneline`, либо честно напиши, что transient state omitted и перед действием его надо перепроверить live-командой;
  - `UNCONFIRMED` оставляй только для реально неизвестных **устойчивых** фактов, а не для того, что можно мгновенно добрать локальной командой.
  - не превращай snapshot в pointer/source из канона, audit-report, merge notes или follow-ups backlog — даже если snapshot “удобно читать”.

## Playbook: Semantic Memory (эвристики)
Цель: чтобы каноника оставалась маленькой, а snapshots — «бэкапом смысла» для handover/history, а не ещё одним уровнем канона.

1) Канон держим маленьким: в каноне — bullets + pointers на канон / audit / follow-up, а детали/эволюция могут жить в snapshots только как handover/history context.
1.1) Snapshot не становится durable pointer'ом:
- range/merge-wave snapshots = history/review context;
- topic-specific snapshots = тоже history/context, а не cited source. Если без snapshot теряется устойчивый факт — значит этот факт надо промоутить в durable doc, а не ссылаться на snapshot.
2) Все тяжёлые tool-output/логи по умолчанию **маскируем**, не пересказываем: `[MASKED: ...]` + путь/команда для воспроизведения.
3) Суммаризация — только когда без неё нельзя продолжать/не помещаемся. Summary пишем как **контекст/инструкции**, не как реплику диалога.
4) Любая новая информация должна попадать в контейнер:
   - `FACT` (устойчивый факт)
   - `DECISION` (принятое решение)
   - `CONSTRAINT` (ограничение)
   - `NEXT` (следующие шаги)
   - `OPEN` (вопрос/неясность)
5) Если сомневаешься — пометь `UNCONFIRMED` и не додумывай.
6) Перед выполнением: «выбери контекст» — не грузить все файлы/логи; читать точечно (JIT) по ссылкам из реестра.
7) Для сложных задач — изоляция: под‑сессия/под‑агент по одной теме → возвращает 10–20 строк итогов + ссылки; результат фиксируем snapshot’ом.

Если нужен “working set” — добавь в этот snapshot ссылки на plan/канон/команды и на предыдущие snapshots (цепочка восстановления).
