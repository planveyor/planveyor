# Playbook: Code review — merge-range (BASE..HEAD)

Шаблон отчёта: `docs/code_reviews/_template_merge_range.md` (или `docs/doc_reviews/_template_merge_range.md` для docs-only range)

Это **не роль**. Это отдельный **шаблон/плейбук** для ревью большого диапазона `BASE..HEAD` после merge/конфликтов.
Роль Reviewer и “обязательный старт” остаются в `docs/roles/reviewer.md`.

Template ownership / resolution:
- shared default для этого шаблона живёт в `docs/code_reviews/_template_merge_range.md`;
- optional repo-profile override, если он когда-либо появится, живёт в `docs/code_reviews/profiles/<repo_profile>/_template_merge_range.md`;
- копии `docs/code_reviews/_template_*.md`, доставленные в проект, считаются mirrored defaults для repo-local flow, а не вторым каноном.
- для docs-only range тот же `profile override -> shared default` contract применяется к `docs/doc_reviews/_template_merge_range.md`.

Если playbook выполняется через Manager merge pipeline:
- Manager запускает шаг и просто ждёт completion;
- mid-run пинги `progress?` / `ETA?` / `blocker?`, `interrupt` и reset running role threads запрещены;
- если Architect по triage считает замечания deferable/non-blocking, merge-range можно закрыть `Done` и идти дальше, даже если follow-up завели;
- если Architect по triage считает, что нужен blocking follow-up, текущий review-only plan получает `Superseded`, tracker не двигается дальше и range review потом запускается заново уже после fix merge; новый follow-up dev-plan стартует с `**Status:** Architect initial draft`.
- merge-range review остаётся единственным live merge-quality truth surface для этого диапазона: single review artifact обязан materialize-ить `Lane synthesis / aggregate verdict` до Architect handoff, а `post_merge_audit` потом читает тот же artifact вместо fresh reviewer rerun.

Стиль отчёта (не переопределяет роль)
- Пиши по‑русски, деловым тоном.
- Фиксируй только проблемы и как исправить (без похвалы).
- Структура: `S1 Blocker / S2 Risk / S3 Nit / Follow-ups`.
- Review artifact тоже держи Russian-first: заголовок, первая summary-строка, range/rerun narration и prose в секциях пиши по-русски; английский оставляй только для команд, путей, кода и literal error strings.
- Если правишь legacy review-file с английскими headings, не делай rename-only churn; но новый текст внутри секций всё равно пиши по-русски.
- Architect later дописывает секцию `Архитектурное ревью` (или сохраняет legacy heading `Arch review`), и этот prose тоже должен оставаться русскоязычным.

Interim artifact status contract (если range review идёт через status-driven reviewer flow):
- один и тот же review-file может быть создан до visual sanity и жить через code-review + visual-review phases;
- `Черновик` — единственный допустимый interim header status, пока visual sanity не закрыт;
- если visual/runtime proof блокируется, тот же файл переводится в `❌ S1 blocker(ы)` и blocker описывается в `## Визуальные доказательства`;
- не выдумывай header-статусы `BLOCKED`, `PARTIAL`, `FROZEN`, `PAUSED` и не заводи второй side-file “для заморозки состояния”.

ВХОДНЫЕ ПАРАМЕТРЫ
- BASE: `<sha>`
- HEAD: `<sha|HEAD>`
- TOPIC (опц.): `<short>`
- EXCLUDE_DOCS (опц.): `<0|1>` (по умолчанию: 1)

ВЫХОДНЫЕ АРТЕФАКТЫ
- Review report: для manual/non-generated merge-range review используем `docs/code_reviews/YYMMDD_HHMM_<TOPIC>.md`, если в range есть хоть один non-doc файл, и `docs/doc_reviews/YYMMDD_HHMM_<TOPIC>.md`, если range docs-only; для generated review-only scaffold from `planveyor_review_range_init()` obey literal path, уже materialized в plan (`docs/doc_reviews/{plan_stem}.md` пока final generated bundle остаётся docs-only, иначе `docs/code_reviews/{plan_stem}.md`)
- Risk packet (после финального review artifact): `docs/reviews/*_risk_packet_range_<base7>_<head7>.md`, generated by `planveyor_review_risk_packet`; packet summarizes exact truth hosts and never replaces the live review verdict.
- Visual evidence (если range трогает runtime UI): скриншоты в `docs/code_reviews/assets/<REVIEW_BASENAME>/` + секция `## Visual evidence` в review report
- Handoff: Architect triage (принять merge “как есть” или оформить follow-up dev-plan’ы)

## Rerun contract (если range review запускается повторно после blocking follow-up)
- Перед чтением diff явно объяви в report `Rerun mode: incremental | full`.
- `incremental` допустим только когда prior accepted artifact уже закрыл исходный range, новый fix narrow и reviewer может аргументированно доверять unaffected surfaces.
- Для `incremental` report обязан содержать:
  - `Baseline artifact`
  - `Rerun scope`
  - `Trusted unaffected surfaces`
  - `Reused evidence`
- `full` означает, что диапазон переигрывается как новый review; prior artifacts можно ссылать только как history, а не как closure-аргумент.
- Если rerun mode не объявлен, это process gap: сначала зафиксируй его в plan/review artifact, потом продолжай.

## Generated review-only scaffold contract
- Если merge-range plan создан через `planveyor_review_range_init()`, scaffold должен уже materialize-ить bounded review contract:
  - literal `Review target: RANGE=...`,
  - literal review artifact machine carriers `**Target:** RANGE=<base>..<head> (EXCLUDE_DOCS=<0|1>)` and `**Spec:** docs/plans/...md`,
  - helper-backed range stats from `planveyor_merge_range_stats_json BASE HEAD` with labels `total_commits`, `first_parent_commits`, `changed_files`, `diffstat_summary`,
  - concrete `## Review artifacts`,
  - `## Problem` / `## Solution (high level)` / `## Scope` / `## Tests` / `## Commands` без template-only дыр на critical path.
- Review artifact path тоже должен materialize-иться truthfully и в одном месте:
  - docs-only generated bundle → `docs/doc_reviews/{plan_stem}.md`;
  - любой final generated bundle с non-doc carrier → `docs/code_reviews/{plan_stem}.md`;
  - generated plan и generated code draft обязаны держать один и тот же literal path.
- Generated code draft держит exact carrier split:
  - live A/M/R/C/Rename paths → `code_draft_meta.targets`;
  - tracked deletions из range → `code_draft_meta.deleted_paths`;
  - review-host family всё ещё считается по full changed-path set, поэтому deleted non-doc path ведёт scaffold в `docs/code_reviews/...`, даже если deleted path не является live target.
- Generated `## Documentation impact / provenance` в plan и code draft должен выводиться из exact filtered target metadata / `code_draft_meta.targets`: process/doc targets (`docs/plans/**`, `docs/playbooks/**`, `docs/tools/**` и т.п.) перечисляются в `Synchronous doc/registry targets`, а scripts/tooling-only range без doc targets получает explicit `N/A (why=...)`, а не stale product-doc claim.
- Exact-bundle helper для review-only range валидирует `code_draft_meta.deleted_paths` against `Review target: RANGE=<BASE>..` when the file is already absent at `HEAD`; не возвращай deleted path в live `targets` ради зелёного bundle check.
- Повторный helper-run для того же range по умолчанию reuse-ит уже существующий scaffold path только когда literal compatibility tuple совпадает полностью: `BASE`, `HEAD`, `EXCLUDE_DOCS`, resolved repo `profile_id`, derived review-host family и explicit rerun carrier tuple.
- Если нужен intentional parallel history, caller делает это только explicit `planveyor_review_range_init --force-new ...`; repeated invocation без flag не считается implicit запросом на новый artifact.
- Same-path default reuse keeps `.planveyor.planpath` on the reused scaffold, but `.planveyor.planpath.log` must not append an exact consecutive duplicate same-path line on that reuse path.
- Если current pass уже rerun после blocker-fix, `planveyor_review_range_init()` принимает только explicit current-flow carrier:
  - `PLANVEYOR_REVIEW_RERUN_MODE=incremental|full`
  - `PLANVEYOR_REVIEW_BASELINE_ARTIFACT=<repo-relative docs/*.md path>` (`incremental` требует baseline обязательно)
  - `PLANVEYOR_REVIEW_PRIOR_ARTIFACTS=path1|path2` (optional repo-relative docs/*.md list)
- Этот carrier materialize-ится literally в generated plan (`Prior review / rerun artifacts`, `Rerun mode`, `Baseline artifact`) и в generated code draft (`## Current-flow rerun lineage`); helper не угадывает lineage из git history, старых plan names или “похожего range”.
- Полное отсутствие carrier = truthful `N/A (first pass)`; partial/malformed carrier = fail-fast до записи scaffold.
- Visual/runtime defaults тоже должны быть truthful:
  - browser lane включай только когда current target объявляет exact reviewer UI lane (login, path и preconditions); иначе оставь explicit `N/A (why=ui lane not declared)`;
  - native/UI target использует только свой declared helper lane, а не generic web fallback;
  - если range non-UI/docs/backend-only или target требует другую repo-local lane, scaffold оставляет explicit `N/A (why)` / target-local note.
- Если generated scaffold этого не сделал, это process gap в tooling contract. Reviewer фиксирует gap в plan/review artifact, но не должен принимать fake defaults как валидный proof lane.
- Generated review artifacts must not use the manual no-origin Spec escape hatch; exact `N/A (origin_plan_state=manual_range_review_no_origin_plan)` is reserved for manual/non-generated range reviews without origin plan, and still requires `**Target:** RANGE=<base>..<head> ...` to match the requested helper range.
- Если scaffold materialize-ит Visual Acceptance для UI range, но сам plan остаётся review-only, `### UI contract checklist` должен быть bounded review-only `N/A (why=...)` или эквивалентным explicit решением. Implementation-specific UI checklist остаётся в затронутых dev-plan’ах.

ЧТО НУЖНО СДЕЛАТЬ

1) Зафиксировать диапазон и список merge-коммитов
   - `git log --oneline --first-parent --merges BASE..HEAD`
   - Если после merge был отдельный “fixup commit” без merge — учесть его в суммарном diff (он попадёт в BASE..HEAD автоматически).

2) Механические проверки до чтения кода (быстро)
   - Сначала определить repo-profile / declared harness из generated scaffold, `PLAN_PATH -> Context links`, profile docs или repo-local `AGENTS.md`. Shared playbook не имеет права молча подставлять Django/web команды для профилей, которые их не объявили.
   - Общие для всех профилей конфликт‑артефакты: `git diff --check BASE..HEAD` и `rg -n "^<<<<<<< |^======= |^>>>>>>> " .`
     - Любые находки `git diff --check` (trailing whitespace, CRLF) — минимум S3 Nit; по blocking merge-tracker lane чистим финальное дерево или заранее фиксируем Architect-approved parity substitute. Для intentional Markdown hard-break whitespace не используем silent waiver: proof должен назвать exact paths и substitute lane.
     - Если cleanup ещё uncommitted внутри bounded dev-plan, local proof может быть только path-bounded: `git diff --check BASE -- <exact targets>`. Это не заменяет финальный merge-range acceptance gate `git diff --check BASE..HEAD` после materialization/commit и не разрешает broad formatter вместо exact target cleanup.
   - Дубли top-level определений (частая ошибка при ручном мерже конфликтов): `<target-declared duplicate checker> BASE HEAD`, только если target объявил такой checker.
   - Быстрый поиск потенциальных секретов выполняй по roots, которые объявил selected project, например: `rg -n -S "(TOKEN|SECRET|PASSWORD|Authorization:|Cookie:)" <declared-root>`.
   - Быстрый поиск риск-паттернов собирай из target-local vocabulary и materialized code roots. Shared playbook не задаёт framework-specific regex.
   - Используй только repo-local baseline из plan/canon; не запускай framework environment checks по инерции.
   - Migration sanity выполняй только когда selected project объявил migration harness и diff реально затрагивает его модели/миграции. Результат и declared command запиши в review artifact.
3) Собрать дифф (без docs/** по умолчанию)
   - Если EXCLUDE_DOCS=1: `git diff -U3 BASE..HEAD -- . ':(exclude)docs'`
   - Иначе: `git diff -U3 BASE..HEAD`

4) Порядок анализа (risk-first, profile-local)
   - Сначала проверяй declared runtime/contract surfaces текущего repo-profile: routing/config/build/import boundaries, generated-vs-source drift, review artifact truthfulness, security/privacy/runtime risk.
   - High-risk surfaces берутся из declared target contract: routing/config/build/import boundaries, state changes, authorization, secrets/PII, data integrity, generated-vs-source drift и UI contracts, если они есть.
   - Shared playbook не добавляет web, native, framework или tooling vocabulary без explicit target-local declaration.

5) Если range затрагивает runtime UI — visual sanity обязателен
   - Это не “опциональная красота”, а финальная post-merge проверка того, что фича реально доехала в merged code.
   - Visual lane должен быть repo-backed: web/browser или native/system helper применяй только когда plan/canon объявляет target и preconditions; non-UI range фиксируй как explicit `N/A (why)`.
   - Checklist, smoke scenarios и runner receipt выбирай только из declared target-local docs. Недоступный declared runner остаётся blocker или current-host diagnostic по правилам target, а не substitute proof.
   - Не нужно прогонять весь smoke corpus: только затронутые секции/claims для этого range.
   - Handoff на Architect допустим только после code review + visual sanity (если UI есть).
   - До запуска proof lane прочитай materialized `## Review visual lane contract` из origin plan: это либо bounded inline `review_visual_lane_contract.v1`, либо hash-bound `review_visual_lane_contract_ref.v1`, который helper безопасно разрешает в единственный full `review_visual_lane_contract.v2`; missing/stale/foreign/hash-mismatched/traversal ref и runtime UI state `missing|malformed|ambiguous` = fail-closed Architect technical gap. Reviewer не восстанавливает команду по памяти, не сканирует assets directory и не ставит `N/A`.
   - Для `available` lane mechanical comparator и human visual review независимы: выполни exact comparator command, затем exact human index command для каждого mandatory mode и инспектируй complete index.
   - В current review artifact запиши parseable comparator claim/result, capture completeness, complete-index inspection, design verdict и finding dispositions. Closing assets должны быть non-empty regular non-symlink files под `docs/code_reviews/assets/<CURRENT_REVIEW_BASENAME>/`; `.tmp/**`, другой review basename, traversal и symlink — только diagnostics/context.
   - Comparator `pass` не закрывает visual lane без human verdict, human screenshots не закрывают lane без comparator `pass`; baseline-update команда никогда не считается closing comparator proof.

6) Если заявляешь “runtime blocker” — проверь в declared runtime/harness

- Используй repo-local verification command из plan, target canon или AGENTS.
- Если command/harness не объявлен, зафиксируй process gap; не подставляй framework-, browser- или tooling-specific default.
- Сохрани exact command, target scope и result в review artifact. Runtime claim без target-declared evidence не считается закрытым.
7) Если диапазон большой — переход на follow-up планы
   - После общего merge-range отчёта создавай отдельные line-by-line планы/отчёты по риск‑доменам (например `security/auth`, `data integrity`), чтобы не размывать фокус.

8) Сформировать отчёт (только проблемы)
   - Формат: `S1 Blocker / S2 Risk / S3 Nit / Follow-ups`, каждая проблема с `file:line`, “почему”, “что сделать”.
   - Имя файла: для manual/non-generated merge-range review — `docs/code_reviews/YYMMDD_HHMM_<TOPIC>.md` (если есть хоть один non-doc файл) или `docs/doc_reviews/YYMMDD_HHMM_<TOPIC>.md` (если range docs-only); для generated review-only scaffold from `planveyor_review_range_init()` — literal path из plan / `## Review artifacts`, который already follows the generated-bundle rule. Если TOPIC не задан — `merge_diff_review`.
   - Если это rerun:
     - `incremental` → явно перечисли, что перепроверено заново, что принято по baseline artifact и почему unaffected surfaces trusted;
     - `full` → явно напиши, что prior artifacts используются только как история, а не как доказательство closure.
   - Для merge-mode final review artifact обязан literal-но содержать `Lane synthesis / aggregate verdict` и по одному provenance record на каждый lane finding/disposition с carrier set `source_lane`, `lane_finding_id`, `synthesis_disposition`, `canonical_ref`, `audit_status`, `followup_plan`; без этого Architect/post-merge handoff считается неполным.
   - Для merge-mode final review artifact top-level `**Target:**` и `**Spec:**` обязательны до `**Status:**`; `**Range:**` можно оставить как legacy/context, но helpers не должны полагаться на него для новых artifacts.
   - Если final verdict = `✅ OK` и lane findings отсутствуют, это всё равно disposition: materialize compact no-findings record (`lane_finding_id: N/A (no lane findings)`, `synthesis_disposition: no_findings`, `canonical_ref: <review_artifact_path>#Lane-synthesis--aggregate-verdict`, lifecycle-aware `audit_status`, `followup_plan: N/A`) вместо legacy `N/A` placeholders.
   - Compact no-findings record may cite exact opened/read source refs plus concise delta/outcome instead of repeating full narrative, but it must not drop lane metadata, target snapshot parity, lane synthesis, canonical provenance, lifecycle status or exact gates.
   - После финального review artifact можно materialize-ить `risk_packet` командой `planveyor_review_risk_packet --range BASE..HEAD --review-artifact <review> --post-merge-audit <audit> --operational-receipt <receipt> --ready-to-push-closeout <closeout> --packetization-report <packetization> [--out <packet>]`; packet должен ссылаться на truth hosts и fail-closed при missing/ambiguous inputs, включая missing/invalid `**Target:**` или `**Spec:**`.
   - Если был visual sanity pass — в `## Visual evidence` обязательно перечисли:
     - declared source scenarios и preconditions,
     - target-required runner receipt, если он есть,
     - что именно перепроверено на merged code,
     - какими screenshot/recording artifacts это доказано.

9) Handoff (после отчёта)
   - Если есть plan (dev или review-only): вписать ссылку на review‑файл в plan → `## Review artifacts`.
   - Если plan **нет**: создать review-only plan по `docs/playbooks/review_scoping_plan.md` (с `**Plan type:** review-only`, `BASE..HEAD` и ссылкой на review‑файл).
   - Если review был `incremental`, Architect/harvest/audit должны читать его как closure blocker scope, а full-wave residual-debt extraction делать отдельно.
   - Если review artifact ещё не materialize-ил `Lane synthesis / aggregate verdict` и exact provenance carriers, handoff в `post_merge_audit` не готов; audit не должен компенсировать этот gap новым запуском Reviewer.
   - В любом случае: “дальше” = Architect triage (и если нужны фиксы — только через follow-up **dev** plan; без “тихих” правок по ходу этого ревью).

## Historical diff-check disposition (optional, same-range only)

Используй этот opt-in carrier только когда exact historical `git diff --check BASE..HEAD` остаётся raw-red из-за byte-bound immutable evidence или intentional Markdown hard breaks. Raw command и его exit остаются primary truth: disposition не делает диапазон synthetic-green и не разрешает переписывать historical bytes.

- Writer — Reviewer в единственном current same-range review artifact, только в `## Historical diff-check disposition (optional)` после landing delivery, который поставил validator/template contract.
- Внутри literal optional H2 разрешены только четыре top-level fields, exact `### Candidate rows` и candidate/nested rows; explanatory prose writer template размещает до H2, чтобы strict parser сохранял fail-closed unknown-row behaviour.
- Reviewer сначала повторяет raw `git diff --check <base>..<head>`, затем materialize-ит полный candidate set. Каждая `- Candidate:` обязана иметь literal nested fields `range`, `raw_command`, `raw_exit`, `path`, `line`, `blob_oid`, `finding_kind`, `provenance_ref`, `provenance_sha256`, `lifecycle`, `reason_code`, `owner`, `action`.
- Все rows держат `lifecycle: candidate`, `owner: Reviewer`, `action: record_candidate`; они сортируются по bytewise `path`, numeric `line`, `finding_kind`, `blob_oid`, `provenance_ref`. `Candidate set SHA-256` — SHA-256 UTF-8 compact JSON массива именно этих 13 typed fields с lexical keys и `separators=(',', ':')`.
- Для Markdown hard break допустим только `reason_code: intentional_markdown_hard_break`, где `provenance_ref` равен reported code-draft path. Для JSON support payload допускаются только `immutable_support_payload_selected_current` либо `immutable_support_payload_historical_or_superseded`; selection выводится validator-ом из target-ref origin plan и plan-resident lifecycle/ref/SHA, не из body `current: true`.
- Пока raw-red candidate set полон, `--historical-diff-check-readback --as-status "Ready for Arch review" --json` даёт только `verified_pending_architect`. Это derived readback, не новый `**Status:**`, aggregate status или `Current state` value.
- Semantic approval принадлежит только Architect: под `## Архитектурное ревью` он добавляет ровно bare literal `Historical disposition approval: state=accepted range=<base>..<head> raw_exit=<n> candidate_set_sha256=<sha256>`. Только после этого `--as-status Done` может вернуть `accepted`.
- `accepted` reconciliate-ит только raw historical diff-check signal: current-proof, canonical header/status-family и independent `Current state: open` blocker gates выполняются до этой projection и не могут быть замаскированы approval.
- Missing, duplicate, stale, foreign, unknown, unsorted или drifted rows/approval fail closed. Не добавляй global ignore, path-prefix waiver, отдельный historical artifact или новую schema/authority surface; такой request возвращается Architect.

## Как заполнять локальные секции sibling

Две секции ниже имеют стабильные заголовки и initial fields. После
`planveyor_consumer_init` их тело принадлежит sibling: внесите target-local
команды, данные, критерии и proof только для этой фазы. Общие lifecycle
правила, статусы и authority остаются вне секций; изменение формата требует
отдельной явной адаптации, а не обычного upgrade.
